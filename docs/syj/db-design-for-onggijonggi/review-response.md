# DB 설계 리뷰 티키타카 — 응답 (라운드 1~8)

옹기종기 팀이 `db-design-for-onggijonggi/` 번들을 자기네 에이전트로 검증한 결과에 대한 응답이다.
**1절**은 llmhub 실제 코드로 검증한 사실(전부 파일:내용 인용 가능), **2절**은 이번 논의에서 새로
제안한 설계(옹기종기 전용, llmhub 코드로 검증된 적 없음)다. 이 둘을 섞어 읽지 않도록 표시를 분리했다.

---

## 1. 1라운드 — 지적 6개 검증 결과

llmhub 실제 마이그레이션(V1~V4)·`IndexingService`·`ChatService`·`PostgresChatHistoryRepository`·
`SecurityConfig`·`ChatSessionJpaRepository`를 직접 열어 대조했다. 추측 없음.

| # | 지적 | 결과 |
|---|---|---|
| 1 | doc 상태 필드 / `idx_run_id` 없음 | 사실이지만 **틀**이 다름 — 아래 상세 |
| 2 | `uploaded_by` FK가 사용자 삭제를 막음 | **틀렸음** — V4에서 이미 `ON DELETE SET NULL`로 해결됨 |
| 3 | `acc_tag` 변경 경로 없음 | **맞음**, llmhub도 미해결 |
| 4 | `chat_msg` 순서가 `created_at`만 의존 | **맞고, 지적보다 심각함** — 아래 상세 |
| 5 | 취소된 응답이 이력에 남을 수 있음 | **틀렸음** — 이미 안전하게 처리됨 |
| 6 | `doc_key` 전역 유니크라 덮어쓰기 위험 | **부분적으로 맞음** — 위협 모델이 admin 전용으로 좁혀짐 |

### 1번 — doc 상태 / idx_run_id: 질문의 틀이 잘못 짜여 있었다

`indexingRunId`는 `IndexingService.run()`이 매 색인마다 `UUID.randomUUID()`로 생성해 **ES 조각에만**
태깅하고 구버전 삭제 판별에만 쓴다. PG엔 원래 없다(grep 0건, 사실).

하지만 llmhub 색인 파이프라인은 팀이 가정한 "다단계 비동기 워커"가 아니다. `IndexController` →
`IndexingService.run()`이 HTTP 요청 하나 안에서 검증→추출→청킹→임베딩→ES색인→PG upsert를 **동기**로
전부 처리한다(주석: "색인은 동기 처리다. 진행률·큐는 없고, 실패하면 에러 응답이다"). 큐도 워커 재개도
없다. `documentRepository.upsert()`가 파이프라인의 맨 마지막이라 그 전에 죽으면 PG 행 자체가
생성/갱신되지 않는다 — "행은 있는데 조각 0개"는 이 구현에서 안 생긴다.

**진짜 위험은 방향이 반대다.** ES 색인 + 구버전 삭제까진 끝났는데 PG upsert 직전에 죽으면, ES엔 이미
`access_tags`까지 박힌 새 조각이 검색 가능한 상태로 올라가 있고 PG엔 그 행이 없거나 옛 메타데이터
그대로인 상태가 남는다. 이건 실제로 미해결 — llmhub 코드에도 `OPEN-QUESTIONS.md`에도 이 케이스를
다루는 자리가 없다. v0가 단일 인스턴스·admin 전용·저빈도라 방치된 것으로 보인다.

→ 옹기종기는 **파이프라인이 실제로 비동기**이므로(2라운드에서 확인) 이 문제가 llmhub보다 훨씬
직접적으로 적용된다. 2절 참고.

### 2번 — `uploaded_by` FK: 이미 해결됨

`V4__document_uploaded_by_on_delete.sql`이 정확히 이 이유로 나중에 추가됐다.

```sql
alter table document drop constraint document_uploaded_by_fkey;
alter table document
    add constraint document_uploaded_by_fkey
        foreign key (uploaded_by) references app_user (id) on delete set null;
```

번들에 V4가 포함돼 있고 `README.md` 용어집에도 `L-5`로 설명돼 있다. **문서 쪽 문제는 남는다** —
`03-data-model.md`의 `document` 표 `uploaded_by` 행에 "ON DELETE SET NULL (L-5)"가 적혀 있지 않아서
스키마 문서만 본 사람에겐 "미정"으로 읽힌다. 다음 갱신 때 추가할 것.

### 3번 — `acc_tag` 변경 경로: 진짜 열린 질문

document의 `access_tags`를 부분 갱신하는 API/서비스가 llmhub 코드베이스에 없다(grep 확인). 유일한
갱신 경로는 재업로드(같은 `doc_key`)뿐이고, 그건 파일 전체를 다시 올려 재임베딩까지 하는 무거운
경로다. "권한만 바뀌었는데 재임베딩까지 해야 하나"는 llmhub도 답을 안 낸 채 방치했다. 옹기종기는
부서 개편·권한 조정이 실제 시나리오라(2라운드 확인) 이걸 먼저 풀어야 한다. 2절 참고.

### 4번 — `chat_msg` 순서: 지적보다 심각함

`PostgresChatHistoryRepository.appendTurn()`은 user 메시지와 assistant 메시지를 **정확히 같은
`Instant now`**로 저장한다(같은 트랜잭션, 변수 재사용):

```java
Instant now = Instant.now(clock);
messages.save(new ChatMessageEntity(UUID.randomUUID(), sessionId, user.role(), user.content(), null, now));
messages.save(new ChatMessageEntity(UUID.randomUUID(), sessionId, assistant.role(), assistant.content(), sourcesJson, now));
```

`seq` 컬럼도 없다. 즉 매 턴마다 두 행이 완전히 동일한 `created_at`을 갖는 게 "가끔 생기는 경우"가
아니라 **설계상 기본값**이다. `ORDER BY created_at ASC`만으로는 동률 순서가 SQL 표준상 보장되지
않는다 — 지금 안 터지는 건 PostgreSQL이 우연히 물리적 삽입 순서로 반환하는 경우가 많아서지, 보장된
동작이 아니다. 옹기종기가 세션 내 단조 증가 `seq`를 지금 넣는 걸 권장한다(2절 체크리스트).

### 5번 — 취소된 응답: 이미 안전함

`ChatService.stream()`에서 이력 저장(`persistHistory`)은 `.doOnComplete()`에만 걸려 있어 스트림이
취소(`SignalType.CANCEL`)되면 절대 호출되지 않는다:

```java
.doOnComplete(() -> {
    log.info("응답 완료 traceId={} answerChars={}", traceId, answer.length());
    persistHistory(sessionId, question, snapshot(answer), sources, traceId);
});
```

잘린 응답은 `chat_message`에 안 남고, `audit_log`에만 `outcome=CANCELLED`로 독립적으로 남는다(별도
`doFinally`, 세션 이력과 무관).

### 6번 — `doc_key` 전역 유니크: 위협 모델이 admin 전용으로 좁혀짐

`/api/index`, `/api/index/**` 전체가 `SecurityConfig`에서 `hasRole("ADMIN")`으로 막혀 있다(경로·메서드
안 가림). 그래서 "일반 사용자가 남의 문서를 노려 교체"하는 경로는 없고, 위협 모델은 **"admin A가
admin B 문서를 실수로/의도로 덮어씀"**으로 좁혀진다. `doc_key`는 시스템 발급이 아니라 **업로드하는
admin이 임의로 정하는 문자열**이다(`IndexController` 주석: "업로드 때 사용자가 정하는 임의의
문자열"). 옹기종기는 admin이 부서별 다수라 이 위협이 실제로 발생한다(2라운드 확인). 2절 참고.

### 작은 것들

- **`adt_log.req_id`**: `jwt.getSubject()`, 즉 keycloak_subject 값 복사. `app_user.id` 아님.
- **`chat_sess.updated_at`**: 앱 레벨. `appendTurn()` 안에서 `session.touch(now)` 호출 → JPA dirty
  checking으로 커밋 시 UPDATE. 트리거 아님.
- **`chat_sess.title`**: 서버가 첫 질문에서 생성(`ChatController.titleOf()`), 60자 넘으면 서로게이트
  쌍 보존하며 자름. `not null`, 클라이언트가 안 보냄.
- **인덱스 정정**: 제안된 `chat_sess(user_id, created_at DESC)`는 실제 쿼리와 안 맞는다. 실제 정렬
  기준은 `updated_at DESC`(`findByUserIdOrderByUpdatedAtDesc`) — 맞는 인덱스는
  `(user_id, updated_at DESC)`. 이 인덱스는 **llmhub 자체에도 없다**(`chat_message(session_id,
  created_at)`만 V2에 있음, `idx_chat_message_session_created`).
- **`emb_mdl` 이름만 기록**: 알려진 사각지대. llmhub `OPEN-QUESTIONS.md`의 **OQ-016**("임베딩 모델이
  같은 이름으로 조용히 바뀔 수 있다 — `bge-m3` 롤링 태그")이 정확히 이 문제이고 아직 미해결.
- **`app_user` 생성 시점**: `keycloak-appuser-provisioning-from-llmhub.md`에 이미 공유함(JIT +
  `on conflict do nothing`). 스키마 문서 자체엔 한 줄도 없는 게 맞음 — 추가 권장.
- **`src_json` 이중화**: 의도된 것. `chat_message.sources_json`은 그 턴에 사용자가 본 근거(UI 재현용),
  `audit_log.sources_json`은 감사용 독립 복사(세션 삭제와 무관하게 남아야 하니 FK 없이 별도 저장).
  `persistHistory`와 `recordAudit`이 같은 `List<Source>`를 각자 `toJson()`으로 따로 직렬화한다.

## 2. 2라운드 — 설계 제안 (옹기종기 전용, llmhub에 없는 새 제안)

> 아래는 llmhub 코드로 검증된 사실이 아니라 **이번 논의에서 새로 제안한 설계**다. 1절과 구분해서 읽을 것.

2라운드에서 옹기종기 에이전트가 "색인 동기/비동기"·"admin 구성"에 따라 1번·6번의 답이 갈린다고
역질문했고, 사용자가 직접 확인했다:

- **색인 파이프라인: 전체가 비동기**(파일 변환뿐 아니라 청킹~임베딩~ES색인까지 격리 워커가 처리)
- **`acc_tag` 변경: 실제 운영 시나리오 있음**(부서 개편·권한 조정)
- **admin: 부서별 다수 예정**

이 답을 전제로 제안한다.

### 2-1. doc 상태 추적 — `status` + `pending_idx_run_id`/`cur_idx_run_id`

> **(4라운드 정정)** 원래 `cur_idx_run_id` 하나만 제안했으나, 이 필드를 런 시작 시점에 덮어쓰면
> "확정된 런" 포인터가 파괴되는 결함이 있었다. 아래는 정정된 버전이다 — 상세 사유는 §5-2 참고.

llmhub의 "동기라 상태 불필요" 논리는 안 넘어간다. 최소 필드를 제안한다.

- **`document.status`**: `PENDING` / `PROCESSING` / `READY` / `FAILED`.
- **`document.status_at`**: 상태 진입 시각. 멈춘 PROCESSING 감지용(§5-2).
- **`document.pending_idx_run_id`**: 지금 진행 중인(아직 완료 안 된) 색인 실행의 식별자. 런 시작 시
  즉시 기록.
- **`document.cur_idx_run_id`**: **마지막으로 성공 확정된** 색인 실행의 식별자. 런이 성공했을 때만
  갱신한다 — 진행 중에는 절대 건드리지 않는다. 정리·재검증 배치가 "지금 살아 있어야 할 조각"을 판단할
  유일한 근거이므로, 진행 중인(아직 안 끝난) run_id로 이 값을 덮으면 아직 서비스 중인 구버전 조각이
  "구버전"으로 오판되어 삭제될 수 있다.
- **`document.last_error`**: 마지막 실패 사유. `FAILED` 상태와 함께 채운다.

**기록 순서는 llmhub과 반대여야 한다.** llmhub은 PG upsert를 맨 마지막에 해서 "성공한 것만 보이게"
했는데, 그건 동기 요청-응답이라 가능했다. 비동기 워커는 **런이 시작될 때 먼저 PG에 `PROCESSING` +
`pending_idx_run_id`를 기록**해야 워커가 죽었을 때 "이 문서가 멈춰 있다"는 게 보인다(§5-2 타임아웃과
함께 동작). 안 그러면 1절 1번에서 llmhub이 걱정 안 한(못 한) "아무 흔적도 없이 그냥 멈춤" 상태가
생긴다.

순서: 런 시작 시 PG `PROCESSING`+`status_at`+`pending_idx_run_id` 기록 → 추출~임베딩 → ES 색인 → ES
구버전 삭제(llmhub의 S17과 같은 원리, `deleteStaleChunks(documentId, indexingRunId)` 참고) → 성공하면
PG `READY`+`cur_idx_run_id`를 `pending_idx_run_id` 값으로 확정, 실패/타임아웃이면 `FAILED`+
`last_error`(이때 `cur_idx_run_id`는 **건드리지 않는다** — 이전 성공 런을 계속 가리켜야 정리 배치가
안전하다).

PROCESSING 중 검색 동작(재업로드 시 구버전 조각을 계속 보여줄지)은 **허용으로 확정**했다 — §5-2 참고.

**개별 시도 이력이 필요하면** `document`에 컬럼을 늘리는 대신, llmhub의 `audit_log`와 같은 패턴으로
**별도 `index_run` 테이블**(`id`, `document_id`, `status`, `error_message`, `started_at`,
`finished_at`)을 두는 방법도 있다. 실패 원인 추적·재시도 판단에 좋고, `document`는 "현재 확정 상태"만
가벼운 필드로 유지할 수 있다. 관측성 요구 수준에 따라 결정할 것(§4 질문).

### 2-2. `acc_tag` 갱신 — "ES 먼저, PG 나중" 규칙

> **(4라운드 정정)** 아래 규칙은 **태그 갱신 자체가 단독으로 일어날 때만** 안전하다. 색인 워커는
> 태그를 복사해 오려고 PG의 `access_tags`를 읽으므로(S18 — PG가 원천), 갱신과 **동시에 재색인이
> 도는 경우**엔 이 순서만으로 막지 못한다. 원래 "PG는 뒤늦게 따라와도 무해하다"고 무조건적으로
> 적었던 건 틀렸다 — 정정하고 실제 안전망(`acc_tag_ver`)은 §5-1에 있다.

> **항상 ES 먼저, PG 나중.** 태그가 좁아지든 넓어지든 이 순서 하나면 **단독 갱신 기준으로는** 안전하다.

- **좁히는 방향(권한 회수)**: ES 조각의 `access_tags`를 먼저 `update_by_query`로 갱신 → 노출이 즉시
  닫힌다. **검색 시점에는** PG를 안 쓰므로(S18 — ES 조각이 실제 필터링 원천) 그 순간 PG가 뒤처져
  있어도 무해하다. 다만 **색인 시점에는** PG를 읽으므로, 동시에 도는 재색인이 옛 태그를 다시 써넣을
  수 있다 — §5-1의 `acc_tag_ver` 정합성 검사가 이 경우의 최종 안전망이다.
- **넓히는 방향(권한 부여)**: 같은 순서라도 피해가 없다 — 부여가 살짝 늦어질 뿐, 과다노출은 없다.
- **재임베딩은 불요**(순수 메타 갱신, llmhub의 `E6`와 같은 원리) — `update_by_query`로 `access_tags`
  필드만 갱신하면 된다.

부분 실패(일부 조각만 갱신되고 중단) 시 재시도·감지 절차는 §5-4 Q3에서 확정했다.

### 2-3. `doc_key` 충돌 방지 — `(department, doc_key)` 복합 유니크

전역 유니크 대신 **`(department, doc_key)` 복합 유니크**로 네임스페이스 자체를 분리한다(대안이던
"글로벌 유니크 + 소유권 검사로 거부(409)"보다 이 방식을 선택함).

- **department 도출**: **(4라운드 정정)** 원래 "요청 시점 JWT claim에서 순수 도출"이라고 적었으나,
  이러면 COMMON처럼 사용자의 기본 소속이 아닌 값은 애초에 도출될 수 없어 §2-3 뒤쪽의 COMMON 설명과
  모순됐다. 실제로는 **업로드 요청이 `department`를 명시 파라미터로 받고, 서버가 요청자의 claim
  집합에 그 값이 포함되는지 검증**한다(다중 부서 소속 admin이 실제로 있어 claim이 다값일 수 있음,
  §5-4 Q2 확정). 검증 자체는 llmhub의 `S4` 원칙과 같은 자리(앞단 게이트)에서 이뤄진다. `app_user`
  테이블엔 저장하지 않는다(`S3` 원칙 — 역할/부서를 저장하면 Keycloak과 이중 관리가 된다) — 이건
  원래 맞았고 그대로 유지.
- **재업로드 시 department는 고정**된다(재파생하지 않음) — §5-3 참고.

**전사 공통 문서**: `(department, doc_key)`만 정하면 부서 공통이 아닌 전사 규정 같은 문서를 특정
부서 소유로 억지로 배정하거나 부서마다 중복 업로드해야 하는 문제가 생긴다. 해결책:

- **`department = 'COMMON'`** 센티널 값을 쓴다. `NULL`은 쓰지 않는다 — 대부분 DB에서 `NULL`끼리는
  유니크 제약상 서로 다른 값으로 취급되어(PostgreSQL 15+의 `NULLS NOT DISTINCT`를 쓰지 않는 한) 같은
  공통 문서를 여러 번 올려도 충돌 감지가 안 된다. 문자열 센티널이 명시적이고 이식성도 좋다.
  `(department, doc_key)` 유니크 제약은 그대로 두면 `('COMMON', 'hr-policy-2026')`도 자기
  네임스페이스를 가져 부서별 키와 충돌하지 않고, COMMON끼리는 충돌 감지가 된다.
- **별도 테이블/스코프 분리는 권장하지 않는다.** 공통 문서도 상태 추적(2-1)·재색인·불변식 로직이
  부서 문서와 동일하므로 네임스페이스만 다르면 충분하다. 테이블을 쪼개면 그 로직을 두 벌 유지해야
  한다.
- **COMMON 쓰기 권한**은 스키마가 아니라 인가(조직 정책) 문제다 — `S4`와 같은 자리(앞단 게이트)에서
  "이 admin의 department claim이 COMMON 쓰기 권한을 포함하는가"를 판정하면 된다. 스키마엔 영향이
  없으므로 지금 결정하지 않아도 마이그레이션이 아파지지 않는다(§4로 이동).

### 2-3a. `document.id`는 서로게이트 UUID로 — (8라운드 전환, 사용자 확정)

> **(8라운드 전환)** 원래 이 자리엔 "llmhub처럼 id를 업무 키에서 결정적으로 유도하되, 유니크 제약을
> 바꾸면 **id 유도·조회·upsert 세 곳**을 함께 고쳐야 한다"는 경고가 있었다. 8라운드에서 **결정적 유도
> 자체를 버리기로** 확정했으므로, 경고 대신 그 판단 근거를 남긴다.

**llmhub이 결정적 유도를 쓴 이유는 소스 주석에 명시돼 있다:**

```java
// IndexingService.run()
// "id는 PG 커밋보다 먼저 필요하다. doc_key에서 결정적으로 유도하므로 upsert 전에 조각을 조립할 수 있다."
String documentId = DocumentId.of(docKey).toString();

// PostgresDocumentRepository.upsert()
// "랜덤이 아니라 doc_key에서 결정적으로 유도한다. 색인 서비스가 커밋 전에 같은 id로 ES 조각을 조립하기 때문이다."
```

즉 **동기 파이프라인에서 PG upsert가 맨 마지막이었기 때문**이다(§1 1번). 그런데 옹기종기는 **런 시작
시 PG 행을 먼저 만드는 순서로 뒤집었으므로**(§2-1) 워커가 PG에서 id를 읽어오면 된다 — **결정적 유도의
유일한 근거가 이미 사라졌다.** 남은 건 비용뿐이었다:

| 결정적 유도가 만들던 문제 | UUID로 바꾸면 |
|---|---|
| 부서 이관 시 업무 키가 바뀌면 **PK가 바뀐다** → 행 교체 + ES 조각 `document_id` 전량 교체 = 사실상 전량 재색인 | `UPDATE document SET department=… WHERE id=…` **한 줄**. ES는 손댈 필요 없음(§5-3) |
| 삭제된 문서와 같은 키로 재업로드하면 **같은 id가 유도돼 PK 충돌**(6라운드에 "부활"로 우회했던 문제) | 충돌 자체가 안 생김(§5-7) |
| id 유도·조회·upsert **세 곳**을 업무 키 변경 시 함께 고쳐야 함 | **두 곳**(조회·upsert)으로 줄어듦 |

**채택**: `document.id`는 **랜덤 UUID**(서로게이트 키). `(department, doc_key)`는 순수 유니크 제약으로만
쓴다(부분 유니크 인덱스 — §5-7).

**남는 주의**: 재업로드 조회와 upsert는 여전히 `doc_key` 단독이 아니라 **`(department, doc_key)` 기준**
이어야 한다. 서로 다른 부서가 같은 `doc_key`를 올렸을 때 `findByDocKey(docKey)` 하나만 보면 남의 부서
문서를 찾아 갱신해 버린다 — 이건 UUID로 바꿔도 그대로 남는 함정이다.

- [ ] `chat_session(user_id, updated_at DESC)` 인덱스 — 1절 작은 것들.

      않는다. 조회·upsert만 `(department, doc_key)` 기준으로 맞추면 된다.
- [ ] `document.department`(문자열, `COMMON` 센티널 허용) + `(department, doc_key)` 복합 유니크 —

      배치도 같이 필요.
- [ ] `document.deleted_at`, `deleted_by` — §5-7 소프트 삭제. **`deleted_by`는 FK가 아니라
      `keycloak_subject` 값 복사**(7라운드 정정 — 감사 목적이므로 `audit_log.req_id`와 같은 형태).
- [ ] `(department, doc_key)` 유니크를 **부분 유니크 인덱스**로: `UNIQUE (department, doc_key) WHERE
      deleted_at IS NULL` — §5-7. 처음부터 이 형태로 만들 것(나중에 바꾸면 기존 인덱스 재생성 필요).

**스키마가 아니라 로직·배치로 들어가는 것**(같이 안 잡으면 필드만 있고 아무도 안 쓰는 상태가 된다):

- [ ] **고아 조각 스위퍼** — `idx_run_id`가 `cur`도 `pending`도 아니면서 `indexed_at`이 유예보다

      처리 주의**(`IS DISTINCT FROM`).
- [ ] **워커 최종 커밋을 조건부 UPDATE로** — §5-8. 읽고-확인-쓰기로 구현하면 TOCTOU다.
      `FAILED` 경로는 **`RETURNING pending_idx_run_id`**로 정리 대상을 먼저 확보할 것(§5-2).
- [ ] **`attempt_cnt` 상한** + 재시도 대상 조회 조건(§5-2).
- [ ] **원본 파일 유예 삭제 배치** — 삭제 후 N일 경과분 정리(§5-7 3단계).

      두는 방식(§5-7, llmhub `IndexingService` 패턴). 안 하면 스토리지 고아가 쌓인다.
- [ ] **복구 API** — 삭제와 같은 권한, 초기화 표대로 필드 리셋, 살아있는 동일 키 존재 시 409(§5-7).
- [ ] **`deleted_at IS NULL`을 리퍼·정합성 배치·목록/상세 조회의 기본 조건으로**(§5-1a).

## 5. 3라운드 — 교차 문제와 나머지 질문 응답

> 이 절도 2절과 같은 성격이다: llmhub 코드로 검증된 적 없는 새 설계.

### 5-1. 결정 1×2 충돌 — 인정, `acc_tag_ver`로 보완

옹기종기 에이전트가 정확히 짚었다: "ES 먼저, PG 나중" 규칙은 **짧은 갱신 창**은 닫지만, 태그 갱신과
**동시에 도는 재색인**이 옛 태그로 새 조각을 색인해버리면 조용히 영구적으로 재노출된다. 순서 규칙만으로는
막을 수 없다 — 채택한다.

**채택하는 보완책:**
- `document.acc_tag_ver`(정수, 태그가 바뀔 때마다 증가) 추가. 조각에도 복사해서 색인 워커가 자기가
  읽은 버전을 박는다.
- **정합성 검사**: `doc_id=X AND acc_tag_ver != doc.acc_tag_ver`인 조각이 있으면 그 조각만 재갱신.
- **(5라운드 정정) `PROCESSING` 중 태그 변경 잠금은 두지 않는다.** 원래 "최소 방어로
  `status=PROCESSING`인 문서는 태그 변경을 거부"를 제안했으나, 이러면 **좁히기(권한 회수)까지
  거부된다** — 회수는 보안 사안인데 "색인 중이라 안 됩니다"로 지연되는 건 방향이 틀렸다. 특히
  §5-2처럼 색인이 비동기·수 분 단위라 지연이 길다. 좁히기·넓히기 **둘 다 PROCESSING 중에도 즉시
  허용**하고, 어긋난 상태는 아래 §5-1a의 2단 검증(자체검증+주기 배치)에만 맡긴다 — 애초에
  `acc_tag_ver` 정합성 검사를 최종 안전망으로 둔 이유가 "순서·잠금이 어긋나도 알아챈다"였으니,
  잠금을 없애도 그 설계 취지는 그대로 유지된다.

### 5-1a. `acc_tag_ver` 정합성 검사 — 실행 주체·주기 (5라운드 추가)

검사 자체(§5-1)는 있었지만 **누가 언제 돌리는지가 없었다.** 이 공백이 곧 과다노출 지속 시간이므로
명시한다.

- **1차: 색인 워커의 자체 검증.** 색인 완료 직후, 자기가 조각에 박은 `acc_tag_ver`와 그 시점의
  `document.acc_tag_ver`를 비교해 다르면 그 자리에서 즉시 재갱신한다. 가장 싸고 즉각적이라 대부분의
  경우를 여기서 닫는다.
- **2차: 주기 배치가 백스톱.** 워커가 죽어서 1차 검증조차 못 한 경우를 청소한다. 배치 주기(몇 분)는
  숫자를 못 박지 않는다 — 조직이 감내할 노출 지속 시간에 달린 문제라 §4로 남긴다.
- 이 재검증도 `access_tags`를 고치는 `update_by_query`이므로, **§5-4 Q3 절차**(태스크 폴링,
  `conflicts=abort`, 갱신 후 카운트 검증)를 그대로 적용한다.

**(7라운드 추가) 이 배치가 고아 조각 스위퍼도 겸한다.** 옹기종기가 "삭제된 문서의 조각이 ES에 남으면
아무도 모른다"는 백스톱 부재를 지적했는데, 확인해 보니 **같은 형태의 구멍이 셋**이었다 — (a) 삭제
직후 좀비 워커가 새 조각을 씀, (b) `delete_by_query` 부분 실패, (c) §5-8이 "이미 쓴 ES 조각은 *가능한
범위에서* 지운다"고 얼버무린 부분과 §5-2의 실패 런 정리 실패. 셋 다 **"어느 런에도 속하지 않는
조각"**이므로 규칙 두 줄로 한꺼번에 닫는다.

> **(8라운드 정정 — 규칙 하나로 줄었다)** 배치는 문서마다 다음을 삭제한다.
> - `idx_run_id`가 **`cur_idx_run_id`도 `pending_idx_run_id`도 아니면서**,
>   `indexed_at`이 **유예 시간보다 오래된** 조각.

`pending_idx_run_id`를 예외로 두는 게 핵심이다. 지금 진행 중인 런이 막 써 넣은 조각을 배치가
"고아"로 오인해 지우면 안 된다. `cur`/`pending` 분리(§2-1 4라운드 정정)가 여기서 한 번 더 값을 한다.

**규칙 2가 규칙 1에 흡수됐다(8라운드).** 원래 "삭제된 문서는 조각 전부 삭제"를 별도 규칙으로 뒀는데,
**삭제 시 `cur_idx_run_id`/`pending_idx_run_id`를 NULL로 만들면**(§5-7) 그 문서의 모든 조각이 자동으로
"cur도 pending도 아님"이 되어 규칙 1에 걸린다. 규칙이 하나로 줄 뿐 아니라 더 정직하다 — 조각이 전부
사라졌는데 `cur_idx_run_id`가 여전히 어떤 런을 가리키는 건 존재하지 않는 것을 가리키는 거짓말이다.

**`indexed_at` 유예가 필요한 이유 — 스위퍼에는 원래부터 경합이 있었다(8라운드 추가).**
옹기종기는 규칙 병합이 "되살아난 문서를 재색인하는 중의 경합을 없앤다"고 봤는데, **없어지지
않는다.** 스위퍼는
문서 상태를 읽고→ES 삭제를 실행하므로, 그 사이에 새 런이 조각을 쓰면 낡은 스냅샷으로 그 조각을 지운다.
그리고 이건 병합 이전에 **규칙 1이 원래 갖고 있던 경합**이다:

```
스위퍼: 문서 X 읽음 → cur=R1, pending=NULL
        ← 이 사이에 새 런 R2 시작, 워커가 R2 조각을 색인
스위퍼: "R1이 아닌 조각 삭제" 실행 → 방금 쓴 R2 조각이 날아감
```

병합은 경합을 **하나로 통일**할 뿐이고, 진짜 해결은 따로 있다 — **조각 나이 유예.** ES 매핑에 이미
`indexed_at`(date)이 있으므로(`es-chunk-index.json`), 스위퍼는 **충분히 오래된 조각만** 지운다.
스위퍼는 백스톱이라 즉시성이 필요 없고, 아직 진행 중일 수 있는 런의 조각은 그 나이에 도달하지 못하므로
경합이 실질적으로 사라진다. **유예값은 리퍼 타임아웃보다 커야 한다**(§4 파라미터 항목 참고).

**구현 함정 — NULL 비교.** 삭제 시 `cur`/`pending`이 NULL이 되므로 규칙 1은 **반드시 NULL을 다루게
된다.** SQL에서 `idx_run_id != NULL`은 참이 아니라 unknown이라 필터가 통째로 안 먹는다 —
`IS DISTINCT FROM`을 쓰거나 NULL을 분기로 처리해야 한다. ES DSL로 짜도 마찬가지로 `must_not terms`에
빈 목록/부재 필드를 넘기는 경우를 명시적으로 처리해야 한다.

**나머지 배치·조회 경로는 `deleted_at IS NULL`을 기본 조건으로 한다.** 소프트 삭제의 고전적 함정이
"검색만 고치고 나머지 쿼리를 안 고치는 것"이라는 지적이 맞다 — 리퍼(타임아웃 회수), `acc_tag_ver`
정합성 검사, 문서 목록/상세 조회 전부 삭제된 문서를 건너뛴다. 위 스위퍼의 2번 규칙만 예외다(삭제된
문서를 **일부러** 찾아야 하므로).

**(4라운드 추가) 불변식 2의 일시 위반을 명시한다.** "ES-먼저, PG-나중" 규칙이 실행되는 동안(그리고
동시 재색인이 겹치는 동안) 조각의 `access_tags`가 상위 `document.access_tags`와 **일시적으로
어긋난다** — 원본 번들 `03-data-model.md`의 불변식 2("조각의 access_tags는 상위 document의
access_tags와 일치한다")는 항상 참이 아니라 **"`acc_tag_ver` 일치 시에만" 참인 불변식으로 다시
읽어야 한다.** 복구 수단은 위 정합성 검사(`acc_tag_ver` 불일치 조각 재갱신)다. onggijonggi가 원본
번들의 불변식 목록에도 이 캐벗을 반영할 것 — 이 파일(`review-response.md`)은 1라운드 산출물
(`03-data-model.md`/`README.md`)을 수정하지 않는다는 원칙이라 여기 문서화만 해 둔다.

### 5-2. 비동기 색인 보완 3가지 — 전부 채택

- **멈춘 PROCESSING 감지**: `document.status_at`(상태 진입 시각) 추가. "N분 초과 PROCESSING = 죽은
  것"으로 판정하는 타임아웃/리스 방식 채택. 재시도 트리거의 전제 조건이므로 필수로 둔다.
  - **(8라운드 추가) 타임아웃은 짧을수록 좋은 값이 아니다.** 짧게 잡으면 **살아 있는 느린 워커를
    죽었다고 오판하는 빈도가 올라가고**, 그 워커가 이미 ES에 써 넣은 조각이 고아가 되어 §5-1a
    스위퍼가 돌 때까지 검색에 노출된다. 아래 "부분 색인 조각의 수명"에서 정정한 방향(짧게 잡아도
    누적은 안 줄어든다)과 합치면 — 타임아웃은 **양쪽에 비용이 있는 값**이고, 짧게 잡을수록 스위퍼
    주기도 함께 짧아져야 한다. 두 숫자는 독립 파라미터가 아니다(§4).
- **PROCESSING 중 구버전 노출 — "허용"으로 확정.** 이건 새 제안이 아니라 **llmhub이 이미 검증해둔
  선택의 재사용**이다. `IndexingService`의 순서(새 조각 색인 완료 → 구버전 삭제 → PG 커밋, `S17`×`S8-3`)가
  정확히 "교체 중에도 뭔가는 계속 검색되게" 하려고 그렇게 짜여 있다. 같은 논리를 그대로 가져간다 —
  비정규화나 검색 시 PG 재조회는 불필요.
- **부분 색인 조각의 수명 — (5라운드 정정) 자가 치유는 "다음 성공한 런"에서만 일어난다는 게 빠져
  있었다.** `deleteStaleChunks`는 **성공한 런 안에서만** 실행되므로, 연속 실패(R2 죽음 → R3 죽음 →
  R4 죽음...)가 이어지면 그사이 실패한 런들의 부분 조각이 **다음 성공까지 계속 누적**된다 — 타임아웃을
  짧게 잡아도 이 누적 자체는 안 줄어든다(타임아웃은 "언제 죽었다고 판단하냐"만 줄인다). **채택하는
  수정**: `FAILED` 확정 시(자체 실패든 타임아웃 회수든) 그 즉시 `doc_id=X AND idx_run_id=<실패한
  pending_idx_run_id>` 조각을 삭제한다. `pending_idx_run_id`를 분리해 둔 덕에 삭제 대상을 정확히
  지목할 수 있다. (잔여 리스크였던 좀비 워커 문제는 §5-8에서, 그 삭제가 실패하는 경우는 §5-1a
  스위퍼에서 각각 해결했다.)
  - **(8라운드 정정) `RETURNING`으로 run id를 먼저 확보해야 한다.** §5-8의 조건부 UPDATE가
    `pending_idx_run_id = NULL`을 함께 쓰므로, 커밋한 뒤에 "어느 런의 조각을 지울지"를 조회하면
    **이미 값이 사라져 있다.** `FAILED` 확정 UPDATE에 `RETURNING pending_idx_run_id`를 붙여 값을 받고
    그걸로 삭제해야 한다 — **리퍼가 회수할 때도 동일**하다. 스위퍼가 백스톱이라 치명적이진 않지만,
    이걸 놓치면 즉시 정리 경로가 조용히 무력화되고 노출 창이 스위퍼 주기까지 늘어난다.
  - **(7라운드 추가) `PENDING`에서 회수할 땐 조각 삭제 단계를 건너뛴다.** `pending_idx_run_id`는
    워커가 실제로 집어서 `PROCESSING`으로 갈 때 기록되므로 `PENDING` 상태에선 아직 `NULL`이고,
    그 시점엔 ES에 쓴 조각도 없다. 두 상태의 회수 절차를 같은 것처럼 적었던 게 부정확했다.
- **`PENDING` 상태의 의미 — (5라운드 추가)** 원래 순서 설명이 런 시작에서 바로 `PROCESSING`으로
  갔는데, 큐 적재~워커 픽업 사이를 나타낼 `PENDING`의 정의가 없었다. `PENDING`=큐에 적재됐지만 아직
  어떤 워커도 집지 않은 상태, `PROCESSING`=워커가 실제로 처리 중인 상태로 정의한다. **`PENDING`도
  타임아웃 대상이다**(워커가 없어 영영 안 꺼내지는 경우) — `status_at` 기준 판정은 `PROCESSING`과
  동일하게 적용한다.
- **`attempt_cnt` 리셋 규칙 — (5라운드 추가)** 런 시작마다 +1. **성공 시 또는 새 파일 재업로드 시
  0으로 리셋**한다 — 둘 다 "새로운 문제의 시작"이므로 이전 실패 이력을 이어가지 않는다.
- **`attempt_cnt` 상한 — (7라운드 추가)** 리셋 규칙만 있고 상한이 없어서 "회수 → 재시도 → 또 실패"가
  무한히 돌 수 있었다. **새 상태를 추가하지 않고 규칙으로 막는다**(상태 축이 늘면 조합이 늘어난다):
  - 재시도 대상 = `status IN ('PENDING','FAILED') AND attempt_cnt < 상한 AND deleted_at IS NULL`
  - 영구 실패 조회 = `status='FAILED' AND attempt_cnt >= 상한` — 운영자가 이 쿼리로 "포기된 문서"를
    본다. 별도 상태값 없이도 완전히 조회 가능하다.
  - 상한값은 타임아웃·배치 주기와 같이 **파라미터**로 남긴다.

### 5-3. `department`를 문서 정체성의 일부로 고정 — 재파생 금지

`doc` 테이블에 `department` 컬럼이 필요하다는 지적을 받아들인다(유니크 제약의 일부이니 당연히
저장돼야 한다 — `app_user`에 저장하지 않는 것(S3)과 문서 메타데이터로 저장하는 것은 다른 층위라
원칙과 충돌하지 않는다).

**"부서 바뀐 admin이 재업로드 못 함"을 버그가 아니라 의도로 확정한다.** `department`는 `doc_key`와
마찬가지로 **문서 정체성의 일부**이므로 재업로드/재색인 때 요청자의 현재 claim에서 다시 파생하지
않는다. 매번 다시 파생하면 복합 유니크 키의 절반이 조용히 바뀌어 기존 행을 못 찾고 **새 문서가
중복 생성**되는 쪽이 진짜 위험이다(llmhub이 `doc_key`를 재업로드에도 안 바꾸는 것과 같은 이유,
`S17`). 부서 이관이 필요하면 별도의 명시적 "이관" 작업으로 다루고, **지금은 만들지 않는다**(v0 패턴 —
자리는 열어두고 구현은 미룬다).

**id 유도 마이그레이션 비용 — 타이밍 확인**: 이미 색인된 문서가 있는 상태에서 `DocumentId` 유도
방식을 바꾸면 기존 `doc_id`가 전부 달라져 전량 재색인이 불가피하다는 지적도 맞다. 옹기종기가 아직
프로덕션 데이터가 없다면 지금이 유일하게 싼 시점이라는 데 동의한다 — 실제로 데이터가 있는지는
onggijonggi 팀만 아는 사실이니 팀이 확인할 것.

**부서 개편 시 운영 대응 — (5라운드 확정)** department가 고정이므로, 부서가 통폐합되면 후신 부서
admin의 claim엔 옛 department 값이 없어 그 문서를 재업로드할 수 없다. 이 경우 **운영자가 DB에서
`document.department` 값을 직접 수정**하는 수동 절차로 대응한다 — 새 기능은 만들지 않는다. 자동화된
"이관" API는 계속 범위 밖으로 둔다(5-3 위 문단과 동일한 v0 원칙).

> **(8라운드 확인) 이 "수동 절차"가 실제로 무엇을 요구하는지 따져봤더니, 서로게이트 UUID 전환의
> 결정적 근거가 됐다.**
> - **결정적 id 유도를 유지했다면**: `department`가 id의 입력이므로 값을 바꾸는 순간 **PK가 바뀐다.**
>   행을 교체하고, ES 조각의 `document_id`를 전부 바꾸고, 옛 doc_id 조각을 손으로 지워야 한다(그 조각은
>   PG 부모가 없어져 §5-1a 스위퍼도 못 잡는다). "수동 절차"가 실제로는 **전량 재색인 + 수동 청소**였다.
> - **서로게이트 UUID로 바꾼 지금**(§2-3a): `UPDATE document SET department=… WHERE id=…` **한 줄로
>   끝난다.** ES 조각은 `document_id`로만 연결되고 **`department`를 들고 있지 않으므로**
>   (`es-chunk-index.json`에 그 필드가 없다 — `access_tags`만 있다) **재색인이 전혀 필요 없다.**
>
> 5라운드에 정한 "운영자가 직접 수정한다"는 결론은 그대로지만, 그게 성립하려면 id가 업무 키에서
> 분리돼 있어야 했다.

### 5-4. 4문항 응답에 대한 채택 여부

- **Q1 (index_run 테이블 vs 컬럼)**: **컬럼 우선 채택.** `status`, `status_at`, `pending_idx_run_id`,
  `cur_idx_run_id`, `last_error`(§2-1 4라운드 정정 버전) + `attempt_cnt`(런 시작마다 +1, 단순 카운터라
  컬럼으로 충분)로 시작하고, **개별 시도별** 사유·소요시간까지 봐야 하면 그때 `index_run`을 추가한다.
  나중에 테이블을 붙여도 기존 컬럼을 안 건드려도 되니 되돌리기 쉬운 방향이라는 근거에 동의한다.
- **Q2 (department claim 출처) — 확정.** **한 admin이 여러 부서에 소속되는 실제 사례가 있다**(팀
  확인). 그래서 department는 JWT에서 순수 파생하지 않는다 — **업로드 요청이 `department`를 명시
  파라미터로 받고, 서버가 요청자의 claim 집합에 그 값이 포함되는지 검증**한다. `COMMON`은 그 값을 쓸
  수 있도록 허가된 사람만 보내는 특수 claim으로 자연스럽게 편입된다(4번 COMMON 권한 질문이 이걸로
  흡수됨, 지적대로). realm role보다는 group 또는 custom claim 중 조직 부서 구조가 계층적이냐 평면이냐로
  고르면 된다는 가이드에도 동의 — 다만 다중 소속이 확인됐으니 어느 쪽이든 **claim이 다값**이라는 전제로
  설계한다.
- **Q3 (update_by_query 부분 실패) — 채택.** 제안된 절차를 그대로 가져간다: `wait_for_completion=false`
  + 태스크 폴링 → `failures[]`/`version_conflicts` 확인 → 좁히기는 `conflicts=abort`(충돌 조각이 옛
  태그를 유지하는 `proceed`는 좁히기에 위험) → 완료 후 `acc_tag_ver` 불일치 카운트로 검증 → **0 확인
  후에만 PG 갱신**. `acc_tag_ver`(5-1)가 있어서 이 검증이 단순 쿼리로 끝난다는 이점도 그대로 살아난다.
- **Q4 (COMMON 쓰기 권한)** — Q2로 흡수. 스키마엔 영향 없지만 **API 계약(업로드 엔드포인트가
  `department` 파라미터를 받고 검증한다)에는 영향이 있다**는 지적을 받아들여 §3 체크리스트가 아니라
  §2-3 설계 자체에 반영했다.

### 5-5. `chat_msg.seq` — 채택 유지, 누락 아님

3절(즉시 반영 체크리스트)에 이미 있다. 2라운드 "결정된 것" 요약에 3가지 새 설계만 강조하느라
재언급을 안 한 것뿐, 채택이 철회된 적 없다.

### 5-6. `chat_message.seq` 발급 방식 — (4라운드 추가) 새로 확정

`seq`를 넣기로 한 것과 별개로 **어떻게 발급할지가 안 적혀 있었다.** `SELECT MAX(seq) WHERE
session_id=X` 후 그 값+1로 INSERT하는 방식은 동시 append에서 경합한다(TOCTOU) — 특히
PostgreSQL 기본 격리수준(READ COMMITTED)에서는 "같은 트랜잭션 안에서 처리한다"는 것만으로는
안 막힌다. 두 트랜잭션이 동시에 같은 MAX를 읽고 같은 다음 값을 계산할 수 있다.

**채택하는 방식:** `chat_session`에 `next_seq`(정수, 기본 0) 카운터를 추가한다. `appendTurn()`이
이미 세션 행을 같은 트랜잭션에서 읽고 갱신(`touch`)하므로, 그 지점에서 원자적으로 카운터를
올린다 — `SELECT ... FOR UPDATE`로 세션 행을 잠그고 읽은 뒤 배정하거나,
`UPDATE chat_session SET next_seq = next_seq + :n WHERE id = ... RETURNING next_seq`처럼 단일 원자적
UPDATE로 확보하는 방식이 더 간단하다. 대안으로 `(session_id, seq)` 유니크 제약 + 충돌 시 재시도도
가능하지만, 재시도 루프가 추가되므로 카운터 방식을 우선 추천한다.

> **(5라운드 정정) 두 가지가 부정확했다.**
> 1. **`+2`로 고정하면 안 된다.** 원본 `04_data.md`의 `chat_message.role`은 `user`/`assistant`/
>    `system` 세 값이라, 이번 턴에 저장할 메시지가 2개라는 보장이 없다. `+2`가 아니라 **`+ :n`**
>    (이번에 실제로 저장할 메시지 개수)으로 파라미터화한다 — 위 SQL도 이미 이렇게 고쳤다.
> 2. **`RETURNING next_seq`는 증가 후 값이다.** 그대로 각 메시지에 배정하면 off-by-one이 난다.
>    `n`개를 저장한다면 그 턴에서 쓸 seq는 `returned-n+1`부터 `returned`까지다(예: `n=2`인 턴에서
>    `returned=10`이면 user=`9`, assistant=`10`). 구현 시 이 배정 공식을 그대로 코드 주석에 남길 것.

### 5-7. 문서 삭제 경로 — (6라운드) 새로 설계

4라운드까지 한 번도 다루지 않았던 항목(§4 의제)을 설계한다. **소프트 삭제로 확정**(사용자 확인) —
채팅 감사(`audit_log`)와는 별개로 문서 업로드/삭제 자체를 감사할 수 있어야 한다는 이유.

- **`document.deleted_at`**(nullable timestamptz), **`document.deleted_by`** 추가.
  **(7라운드 정정) `deleted_by`는 FK가 아니라 `keycloak_subject` 값 복사다.** 원래 `uploaded_by`처럼
  `app_user` FK + `ON DELETE SET NULL`로 뒀는데, 그러면 **삭제한 사람의 계정이 지워질 때 감사 기록이
  같이 사라진다** — 소프트 삭제를 택한 이유 자체가 "삭제를 감사할 수 있어야 한다"였으므로 자기모순이다.
  §1에서 확인했듯 `audit_log.req_id`가 정확히 이 이유로 FK가 아닌 값 복사다. `uploaded_by`는 성격이
  "참조"라 SET NULL이 맞고, `deleted_by`는 성격이 "감사"라 값 복사가 맞다.
- **삭제 권한 — (7라운드 확정, 사용자 확인) 자기 `department` 문서만 삭제할 수 있다.** 업로드와 대칭
  이며, 이미 확정한 "요청의 `department`를 요청자 claim 집합으로 검증"하는 메커니즘(§5-4 Q2)을 그대로
  재사용한다. 별도 권한 체계를 만들지 않는다. `COMMON` 문서는 `COMMON`을 쓸 수 있는 사람만 삭제할 수
  있다 — 업로드와 완전히 같은 판정이다.
- **삭제 순서**: llmhub 자신의 `OPEN-QUESTIONS.md`가 이미 이 순서를 정해 뒀다 — **ES 조각 → PG →
  원본**("중간 실패 시 고아 원본이 남는 편이 고아 조각이 남는 것보다 안전"). 그대로 가져온다:
  1. `doc_id=X`의 ES 조각을 **전부**(현재 확정된 `cur_idx_run_id` 것이든, 마침 진행 중이던
     `pending_idx_run_id` 것이든) 즉시 삭제 — 노출을 즉시 닫는다. **소프트 삭제는 PG 행에만
     적용된다 — ES 조각은 하드 삭제.** 검색 노출은 ES가 결정하므로(S18) 지연 없이 지워야 한다.
     **(7라운드 추가)** 이 `delete_by_query`에도 **§5-4 Q3 절차를 그대로 적용**한다(태스크 폴링 →
     `failures[]` 확인 → 완료 후 잔여 조각 카운트 0 검증). Q3를 태그 갱신에만 걸어 뒀던 게 누락이었다.
  2. `document.deleted_at`+`deleted_by` 기록(PG 행 자체는 유지 — 소프트 삭제). **(8라운드 추가) 이때
     `cur_idx_run_id`와 `pending_idx_run_id`를 함께 `NULL`로 만든다** — 조각을 전부 지웠으므로 그
     포인터는 존재하지 않는 것을 가리키게 된다. 이 한 수로 §5-1a 스위퍼의 규칙 2가 규칙 1에 흡수되어
     1단계가 부분 실패해도 자동으로 회수된다.
  3. 보관 원본 파일은 **바로 지우지 않는다 — (7라운드 확정, 사용자 확인)** N일 유예 후 별도 배치가
     삭제한다. 유예 기간 안에는 보관 원본으로 재색인해 **복구할 수 있다**(수단은 아래 복구 API).
     즉시 지우면 ES 조각·원본이 모두 사라져 소프트 삭제가 순수 감사용으로만 남는데, "잘못 올린 문서
     회수"가 삭제의 주요 동기였던 만큼 "잘못 지운 문서"도 같은 무게로 다뤄야 한다. 유예 기간(N일)은
     파라미터.
- **PROCESSING 중 삭제 요청도 즉시 허용한다** — §5-1의 "관리 조작을 색인 진행 중이라고 지연시키지
  않는다"는 원칙을 그대로 적용. 진행 중이던 워커가 나중에 결과를 커밋하려 할 때 자기 결과를 버리게
  만드는 절차는 §5-8(펜싱)에서 통합해 다룬다.
- **삭제는 `status`를 건드리지 않는다 — (7라운드 추가.)** 색인 수명주기(`PENDING`→`PROCESSING`→
  `READY`/`FAILED`)와 삭제 여부는 **직교하는 축**이라, 삭제했다고 상태를 바꾸면 두 개념이 한 컬럼에
  섞인다. 삭제된 문서가 `PROCESSING`인 채 굳어도 무해하다 — 리퍼·정합성 배치·목록 조회가 전부
  `deleted_at IS NULL`을 기본 조건으로 하므로(§5-1a) 아무도 그 행을 건드리지 않고, 복구하면 어차피
  아래 목록대로 초기화된다.
- **검색 쿼리에서 `deleted_at`을 체크하지 않는다 — 단 (7라운드 정정) 근거가 반대다.** 원래
  "1단계에서 이미 하드 삭제했으므로 검색에 안 걸린다"고 적었는데, 이건 **삭제가 항상 성공한다는
  전제**라 틀렸다. 정확한 근거는 그 반대다 — 검색은 구조상 PG를 보지 않으므로(S18) `deleted_at`을
  **체크할 방법이 애초에 없고**, 그렇기 때문에 **ES 조각 삭제가 반드시 백스톱돼야 한다**(§5-1a
  스위퍼). 결론(검색 쿼리는 안 고친다)은 같지만, 그 결론이 성립하려면 백스톱이 필수라는 게 핵심이다.

### 삭제된 키를 다시 쓸 때 — "부활"을 폐기하고 둘로 가른다 (8라운드 전환)

> **(8라운드 전환)** 6라운드엔 "**재업로드 시 PK 충돌**이 나므로 소프트 삭제 행을 **부활**시킨다"고
> 적었다. 이 함정은 **id를 서로게이트 UUID로 바꾸면서 소멸했다**(§2-3a) — 같은 키를 다시 올려도
> 유도되는 id 자체가 없으므로 충돌할 것이 없다. 그리고 부활을 다시 보니 **더 나쁜 문제가 있었다.**

**부활은 삭제 감사 기록을 지운다.** `deleted_at`/`deleted_by`를 `NULL`로 되돌리면 "언제 누가 지웠나"가
사라진다 — **소프트 삭제를 택한 이유(삭제를 감사할 수 있게)와 정면으로 충돌한다.** 부활은 애초에
PK 충돌을 피하려던 우회였고, 그 이유가 사라진 지금은 남길 이유가 없다. 두 동작으로 가른다.

| 상황 | 동작 |
|---|---|
| 삭제된 문서와 **같은 키로 새로 업로드** | **새 행을 만든다.** 부분 유니크 인덱스(`WHERE deleted_at IS NULL`)라 허용된다. 옛 삭제 행은 기록으로 그대로 남고, 조각도 `document_id`가 달라 섞이지 않는다 |
| **지운 걸 되돌리고 싶다** | **복구 API로만.** 명시적 의도일 때만 `deleted_at`을 되돌린다 |

**복구 API 명세**
- **권한**: 삭제와 동일 — 자기 `department` 문서만, `COMMON` 문서는 `COMMON` 권한자만(§5-7 위).
- **동작**: 보관 원본은 그대로 두고(경로 불변) 아래 표대로 필드를 초기화한다. `status=PENDING`이
  되므로 색인 큐가 집어가 자동으로 재색인된다 — 별도 재색인 트리거가 필요 없다.
- **거부 규칙(409)**: 같은 `(department, doc_key)`에 **살아있는 행이 이미 있으면 거부**한다. 삭제 후
  같은 키로 새로 올린 상태에서 옛 행을 복구하면 부분 유니크 인덱스를 위반하기 때문이다.
- **유예 기간이 지나 원본이 삭제됐으면** 복구는 불가능하다(재색인할 원본이 없다). 그 경우도 409/410
  으로 명확히 거부한다 — 행만 되살아나고 조각이 영원히 안 생기는 상태를 만들면 안 된다.

**(7라운드 추가 → 8라운드에서 복구용으로 이관) 복구 시 초기화 목록.** 삭제 1단계가 ES 조각을
**전부** 지웠으므로, `deleted_at`만 되돌리면 나머지 필드가 존재하지 않는 조각을 가리키며 거짓말을
한다. 복구는 **"완전히 새 문서처럼"** 시작해야 한다.

| 필드 | 복구 시 | 왜 |
|---|---|---|
| `deleted_at` · `deleted_by` | `NULL` | 되살아났으므로 |
| `cur_idx_run_id` | `NULL` | 그 런의 조각은 하나도 안 남았다. 안 지우면 §5-1a 스위퍼가 "이 런 조각은 살아 있어야 한다"고 오판한다 |
| `pending_idx_run_id` | `NULL` | 진행 중이던 런이 있었어도 §5-8이 이미 무효화했다 |
| `last_error` | `NULL` | 이전 실패는 이 문서의 현재 상태가 아니다 |
| `status` | `PENDING` | 삭제 직전이 `FAILED`였을 수도 있다. 새 색인 대기로 되돌린다 |
| `attempt_cnt` | `0` | 새 색인의 시작이므로 §5-2의 리셋 규칙이 그대로 적용된다 |
| `acc_tag_ver` | **유지(리셋 금지)** | 단조 증가여야 한다. 되돌리면 어딘가 살아남은 stale 조각의 버전이 새 버전과 우연히 같아져 §5-1a 정합성 검사를 통과해 버린다 — 이 스위퍼가 성립하는 전제 자체가 깨진다 |

**`(department, doc_key)` 유니크 제약도 정정이 필요하다** — 소프트 삭제된 행이 여전히 테이블에
남아 있으므로, 부분 유니크 인덱스로 바꾼다: `UNIQUE (department, doc_key) WHERE deleted_at IS NULL`.
살아있는 행끼리만 유니크를 강제하고, 삭제된 행은 제약에서 빠진다. **(8라운드) 이 부분 인덱스가
"삭제된 키로 새 행 만들기"를 가능하게 하는 바로 그 장치다** — 위 표의 첫 줄이 성립하는 근거이고,
동시에 복구 API가 409로 거부해야 하는 이유이기도 하다.

**(8라운드 추가) 보관 원본이 새 나가지 않게 — llmhub이 이미 푼 문제다.** 유예 삭제 배치는
`deleted_at`을 기준으로 도는데, **살아있는 문서에 새 파일을 재업로드해 `original_path`가 바뀌면**
옛 원본 파일은 어느 행에서도 참조되지 않으면서 `deleted_at`도 없어 **배치가 영영 못 찾는 스토리지
고아**가 된다. llmhub은 이걸 이미 밟고 이렇게 처리한다:

```java
// IndexingService.run() — "재업로드로 새 원본을 저장했다면 구 원본을 정리한다.
//                          재색인은 같은 키를 재사용하므로 지우지 않는다."
String previousStorageKey = documentRepository.findByDocKey(docKey)
        .map(DocumentRecord::storageKey).orElse(null);   // upsert가 덮어쓰기 전에 확보
...
if (previousStorageKey != null && !previousStorageKey.equals(document.storageKey())) {
    fileStorage.delete(previousStorageKey);
}
```

같은 처리를 하면 된다 — **upsert 전에 이전 저장 키를 확보해 두고, 값이 바뀌었을 때만 구 원본을
지운다**(재색인은 같은 키를 재사용하므로 지우면 안 된다). 참고로 "삭제된 키로 새 행 만들기" 경로는
이 문제가 없다 — 옛 행이 삭제 상태 그대로 남아 유예 배치가 정상적으로 옛 원본을 정리한다.

### 5-8. 좀비 워커 펜싱 — (6라운드 설계 → 7라운드 정정) 조건부 UPDATE로 해결

§5-2(잔여 리스크로 남겨둠)와 §5-7(진행 중 삭제 요청)이 **같은 문제**를 공유한다 — 워커가 마지막
커밋을 하려는 시점에, 그사이 다른 주체(리퍼·삭제 요청)가 이 런을 이미 무효로 만들었을 수 있다.
하나의 메커니즘으로 묶는다.

**(7라운드 정정) 원안이 TOCTOU였다.** 6라운드엔 "최종 PG 커밋 직전 문서 행을 **다시 읽어** 세 조건을
재확인한다"고 적었는데, 이건 전형적인 check-then-act다 — 읽기와 쓰기 사이에 삭제 요청이 끼어들면
`deleted_at`은 찍혀 있는데 `status=READY`인 모순 상태가 만들어진다. **§5-6에서 `MAX(seq)` 읽고-쓰기를
정확히 같은 이유로 배제해놓고 여기선 같은 실수를 했다.**

**채택하는 방식**: 확인과 쓰기를 **단일 조건부 UPDATE**로 합친다. 워커의 최종 커밋은 이 한 문장이다.

```sql
UPDATE document
   SET status = 'READY', cur_idx_run_id = :runId, pending_idx_run_id = NULL, status_at = now()
 WHERE id = :docId
   AND status = 'PROCESSING'          -- 리퍼가 이미 FAILED로 회수하지 않았는지
   AND pending_idx_run_id = :runId    -- 다른 런으로 대체되지 않았는지
   AND deleted_at IS NULL             -- 그사이 삭제되지 않았는지
```

**`affected rows = 0`이면 이 런은 무효화된 것으로 판정**하고 워커는 결과를 버린다. `FAILED` 확정도
같은 형태의 조건부 UPDATE로 쓴다. "읽어서 확인한다"가 아니라 **"조건부로 쓰고 결과를 본다"**가 핵심이다.

**단, 이건 PG만 원자적으로 막는다.** 워커가 이미 ES에 써 넣은 조각은 이 UPDATE로 못 되돌린다 — 무효화
판정 후 스스로 지우려 해도 그 시점에 워커가 죽으면 못 지운다. 그래서 **§5-1a의 고아 조각 스위퍼가
이 경우의 최종 회수 장치**다(그 조각의 `idx_run_id`는 `cur`도 `pending`도 아니게 되므로 자동으로
스위퍼 1번 규칙에 걸린다). 6라운드에 "가능한 범위에서 지운다"고 얼버무린 자리가 이걸로 채워진다.

이 재검증 지점 하나가 좀비 워커 문제와 삭제-중-색인 경합을 동시에 막는다 — 별도 장치 두 개를 만들
필요가 없다.

**(7라운드 관찰) 스위퍼가 완전한 이유.** §5-1a 스위퍼는 PG 문서를 순회하므로 "PG 행이 아예 없는 ES
조각"은 원리적으로 못 잡는다. 그런데 이 설계에선 그런 조각이 **생길 수 없다** — 런 시작 시 PG에 먼저
기록하고(§2-1), 삭제도 소프트라 행이 남으므로 **모든 ES 조각에는 반드시 PG 부모가 있다.** 1라운드 §1에서
지적했던 llmhub의 미해결 결함(ES는 커밋됐는데 PG가 못 따라가 유령 조각이 남는 상태)이 "PG 먼저" 순서를
택한 순간 구조적으로 사라진 것이고, 그 덕에 PG를 순회하는 스위퍼만으로 커버리지가 완결된다.

> **(8라운드 추가) 제약 — `document` 행은 하드 삭제하지 않는다.**
> 위 완결성은 **"소프트 삭제 행이 사라지지 않는다"에 전적으로 의존한다.** 나중에 누군가 "삭제된 지
> N년 지난 행 purge" 같은 보존 정책을 넣으면, **그 순간 부모 없는 조각이 다시 가능해지고 스위퍼는
> 원리적으로 못 잡는다** — 1라운드에서 짚었던 유령 조각 결함이 그대로 돌아온다.
>
> 그러므로 이건 **명시적 제약으로 기록한다: `document` 행은 하드 삭제하지 않는다.** 부수적으로
> `document` 테이블은 삭제된 행이 쌓이며 **단조 증가**한다는 뜻이기도 하다. 언젠가 정말 정리해야
> 한다면 **행 purge와 함께 그 문서의 ES 조각을 먼저 지우는 절차를 세트로** 만들어야 하고, 그 전엔
> 지우면 안 된다. 조용히 깨질 불변식이라 여기 남긴다.
