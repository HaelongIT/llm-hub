# 함정 지도 — llmhub이 실제로 밟은 것들

> llmhub `docs/LEARNINGS.md`(65항목)에서 **다른 팀에도 그대로 유효한 것**을 골라, llmhub 전용 코드
> (S·E·R·L·F·OQ 등)와 클래스명을 걷어내고 주제별로 다시 엮은 것이다. 원문은 `reference/LEARNINGS.md`.
>
> **읽는 법:** 규칙 목록으로 읽으면 안 지켜진다. **증상 목록으로 읽는다** — 그 상황이 왔을 때 알아보면 된다.
> 처음엔 목차만 훑고, 증상이 나타나면 그때 해당 항목을 편다.
>
> 각 항목 끝의 `원문:` 줄로 `reference/LEARNINGS.md`에서 전문을 찾을 수 있다.
> 프레임워크 실제 API 이름(`subscribeOn`·`doFinally`·`useChat` 등)은 일부러 그대로 뒀다 — 팀도 같은
> 이름을 쓰므로 바꾸면 오히려 못 찾는다.

# 1. 조용한 실패 — 에러 없이 잘못되는 것

> 이 묶음이 제일 값지다. 나머지는 터지면 알지만, 여기 있는 것들은 **터진 줄도 모른다.**

<a id="1-1"></a>
## 1-1. 업로드가 200으로 성공했는데 색인이 하나도 안 됐다

- **증상:** 관리자가 파일을 올렸고 200 OK + 빈 본문. 그런데 문서도 조각도 없다. 관리자는 성공으로 읽는다.
- **원인:** 멀티파트 파트는 있는데 내용 스트림이 **비어 있으면** `DataBufferUtils.join()`이 **빈 Mono**를
  낸다. 그러면 뒤의 `map`·`flatMap`이 통째로 건너뛰어지고 핸들러가 아무 값도 내지 않는다. WebFlux는
  빈 `Mono<T>`를 **200 OK + 빈 본문**으로 내보낸다.
- **처방:** `.defaultIfEmpty(new byte[0])`로 빈 바이트를 흘려보내 검증기가 거부(400)하게 한다.
  인코더 동작에 기대지 말고 **구조로** 막는다.
- **일반화:** 리액티브에서 **"아무 일도 없었다"는 성공으로 보인다.** `Mono.empty()`가 흐르는 모든
  `flatMap` 체인이 조용한 200의 후보다. `join`·`next`·`filter` 뒤에는 빈 흐름이 무엇을 의미하는지 정한다.

> 원문: 2026-07-10 「BUG — 빈 Mono는 200 OK가 된다 (`DataBufferUtils.join`의 조용한 성공)」

<a id="1-2"></a>
## 1-2. 조각 텍스트에 �(U+FFFD)가 섞여 있다 — 예외는 없다

- **증상:** 색인된 조각 경계에 치환 문자가 남는다. **예외는 전혀 발생하지 않는다.** 영어에서는 거의
  드러나지 않고 **한국어에서만** 터진다.
- **원인:** Spring AI `TokenTextSplitter`는 텍스트를 **바이트 수준 BPE 토큰**으로 인코딩한 뒤 토큰 목록을
  잘라 조각별로 디코딩한다. 한글 한 글자는 여러 토큰에 걸치므로 조각 경계가 글자 중간을 자른다.
  실관측: `[…근로기준법에 �]` / `[�라 부여한다…]` — "따"가 두 동강 났다.
- **처방:** 토큰은 **크기를 재는 데만** 쓰고, 자르는 위치는 **문장 → 단어 → 코드포인트** 순으로 내려가며
  찾는다. 글자 안쪽을 자르지 않으므로 손상이 구조적으로 불가능해진다. 손상 여부를 단언하는 **불변식
  테스트**를 따로 둔다(손상은 예외가 아니라 치환 문자로 나타나므로 테스트로만 잡힌다).
- **확장:** 토큰 단위로 텍스트를 자르는 **모든 지점**에서 같은 함정을 의심한다 — 임베딩 입력 절단,
  컨텍스트 윈도우 절단, 프롬프트 트렁케이션.

> 원문: 2026-07-10 「IDX — Spring AI `TokenTextSplitter`는 한국어 글자를 조각 경계에서 깨뜨린다」

<a id="1-3"></a>
## 1-3. 마이그레이션엔 있는 컬럼이 항상 NULL이다

- **증상:** 문서 4행, 해당 컬럼이 채워진 행 **0**. 삽입도 조회도 성공한다.
- **원인:** 스키마엔 컬럼이 있는데 엔티티에 매핑이 없다. **테스트가 절대 못 잡는다** — 실패하는 동작이
  하나도 없기 때문이다.
- **처방:** **스키마와 엔티티의 컬럼 집합을 대조하는 것이 유일한 방법이다.** 주기적으로 한다.
- **더 컸던 문제:** 그 컬럼("누가 올렸나")이 관리자의 색인 행위가 남을 **유일한 자리**였다. 즉 컬럼이
  비어 있다는 것은 매핑 누락이 아니라 **감사 공백**이었다. 조용한 NULL은 그 자체보다 그것이 가리는
  것이 문제다.

> 원문: 2026-07-10 「DATA — 스키마에 있는 컬럼이 코드에 없으면 조용히 NULL로 남는다」

<a id="1-4"></a>
## 1-4. 임베딩 뒷단을 바꿨는데 재색인 대상이 0건이다

- **증상:** 게이트웨이 뒷단 임베딩 모델을 갈아끼웠는데 stale 목록이 비어 있다. 에러도 없다.
- **원인:** 조각 메타에 박히는 임베딩 모델명이 **게이트웨이에 넘기는 논리 이름**이었다(실제 값이
  `placeholder-embedding-model`이었다). 실제 모델은 게이트웨이 설정이 들고 있고 코어는 그 존재를 모른다.
  stale 판정은 논리 이름끼리 비교하므로 **뒷단만 바꾸면 이름은 그대로** → 대상으로 안 잡힌다.
  색인 벡터와 질문 벡터가 **다른 공간에 있는데 에러도 stale도 없다.** 차원이 우연히 같으면 차원 가드도
  안 걸린다.
- **처방:** 코드가 아니라 **이름을 고쳤다.** 임베딩 논리명이 **실제 모델을 가리키게** 한다. 그러면 뒷단을
  바꿀 때 이름도 바꾸게 되고 기존 판정이 되살아난다.
  **실증:** 이름을 고친 직후 기존 문서 5건이 전부 stale로 잡혔다(이전엔 0건).
- **비대칭은 의도다:** 채팅 논리명은 **고정**해도 된다 — 어디에도 저장되지 않으므로 뒷단 교체가 설정
  세 줄로 끝난다. 임베딩 논리명만 실제 모델을 가리켜야 한다 — **그 이름이 데이터 계약이기 때문이다.**

> 원문: 2026-07-13 「게이트웨이 뒷단을 원격으로 열다 — 그리고 S8-4의 방어선이 비어 있었다는 것」

<a id="1-5"></a>
## 1-5. 청킹 전략을 바꿔도 재색인 대상에 안 뜬다

- **원인 둘:** (1) 청킹 버전 값이 **저장소 계층의 상수**에서 왔고 재색인이 그것을 갱신하지 않았다.
  (2) 그 상수는 실제 청킹 전략과 **아무 연결이 없다** — 전략을 교체해도 상수는 그대로다. 그런데 상수 옆
  주석은 "전략이 바뀌면 이 값으로 재색인 대상을 식별한다"고 **주장**하고 있었다.
- **처방:** "무엇으로 색인했는가"를 기록하는 필드는 **그것을 실제로 수행한 컴포넌트가 알려줘야 한다.**
  전략에 `version()`을 두고 색인할 때마다 넘긴다(임베딩 쪽과 대칭으로).
- **주의:** 값을 바꾸면 **이미 색인된 모든 문서가 갑자기 재색인 대상**이 된다. 청크 크기 같은 파라미터는
  버전에 넣지 않는다.

> 원문: 2026-07-10 「IDX — 상수로 박힌 "버전"은 버전이 아니다」

<a id="1-6"></a>
## 1-6. 운영자가 설정을 바꿔도 아무 일이 없다

세 가지 형태로 전부 겪었다. **"설정이 존재한다"와 "그 설정이 코드 경로에 닿는다"는 다르다.**

- **(a) `.env`엔 있는데 compose `environment:`에 배선되지 않음** → 컨테이너 안에 그 변수가 없다.
  개발은 앱을 소스로 돌려 `.env`를 직접 읽으므로 **개발에서만 참**이었다. 실측 8개+ 누락.
- **(b) 키는 있는데 코드가 리터럴로 하드코딩** → 검색 분석기가 코드에 박혀 있었고 대응 환경변수는
  **읽는 코드가 없는 죽은 설정**이었다.
- **(c) `application.yml`이 리터럴을 박아 env 참조를 안 함** → `.env` 값이 무시된다. 기능 변화가 없어도
  **설정이 있는데 무시되는 것 자체가 운영자를 오도한다.**
- **처방:** `.env` / `application.yml` / compose `environment:` / **실제로 읽는 코드**, 넷을 주기적으로
  대조한다.
- **검증은 결과로:** "설정을 넣었다"가 아니라 **ES 매핑을 실제로 읽어** 분석기가 반영됐는지 확인했다.
  컨테이너 확인은 `docker compose config`보다 `docker exec <c> env | grep KEY`가 확실하다.

> 원문: 2026-07-11 「배포 설정 위생 — 설정이 코드에 닿지 않으면 없는 것이다 (R-6, R-7, R-15)」 ·
> 2026-07-10 「OPS — 문서가 이름까지 댄 설정이 죽어 있었다」

<a id="1-7"></a>
## 1-7. 커밋 훅이 통과했는데 금지된 것이 들어갔다

- **증상:** 테스트 비활성화 애노테이션이 붙은 파일이 **실제로 커밋됐다.** 훅은 조용히 통과했고 실패했다는
  신호조차 없었다.
- **원인:** diff에서 추가 줄만 고르려고 `grep -E '^\+' | grep -v '^\+\+\+'`를 썼다. **GNU BRE에서 `\+`는
  리터럴 `+`가 아니라 "1회 이상" 수량자**다. 그래서 `^\+\+\+`가 헤더뿐 아니라 `+`로 시작하는 **모든 줄**에
  매치되어 검사할 내용이 하나도 남지 않았다.
- **처방:** diff 파싱은 전부 `grep -E`(ERE)로 통일하고 헤더는 경로 접두사까지 정확히 제외
  (`^\+\+\+ b/`, `^--- a/`).
- **핵심:** **안전장치는 반드시 위반을 주입해 검증한다.** "훅이 통과했다"는 "위반이 없다"가 아니라
  **"훅이 아무것도 안 했다"** 일 수 있다.

> 원문: 2026-07-10 「INFRA — `grep -v '^\+\+\+'`는 diff의 모든 추가 줄을 지운다 (안전장치가 조용히 무력화됨)」

<a id="1-8"></a>
## 1-8. 팀원이 클론하니 훅이 안 돈다 (에러도 없다)

> 팀 프로젝트라면 **이것부터 확인한다.** 사람이 늘어나는 순간 제일 먼저 터지는데 알아챌 신호가 없다.

- **증상:** mac에서 클론해 `./gradlew`를 돌리니 permission denied. 더 나쁜 쪽은 훅이다 — **POSIX에서 git은
  실행 비트 없는 훅을 에러 없이 건너뛴다.** 훅 경로를 설정해도 **커밋은 성공하고 훅만 안 돈다.**
  비밀정보 차단·테스트 강제가 **조용히 전부 꺼진다.**
- **원인:** Windows는 `core.filemode=false`라 git이 실행 비트를 추적하지 않는다. 최초 커밋 때 스크립트가
  인덱스에 `100644`로 굳고, Windows에선 파일 모드 개념이 없어 **아무 증상이 없다.** 이 레포에선 shebang
  추적 파일 4개 중 2개가 644였다 — **즉 우연에 달린 문제다.**
- **처방:** `chmod +x`는 `filemode=false` 하에서 git이 무시한다(워킹트리만 바뀐다).
  **`git update-index --chmod=+x <path>`만 통한다** — blob 해시는 그대로고 모드만 바뀐다.
- **줄바꿈도 함께:** `core.autocrlf=true` + 루트 `.gitattributes` 부재 = 워킹트리 CRLF. POSIX로 새어 나가면
  `bad interpreter: ^M`이다. `*.sh text eol=lf` + 훅 경로 지정으로 고정한다. **blob이 이미 LF면 diff가
  생기지 않아** 유령 수정 걱정 없이 넣을 수 있다. `.gitattributes`로는 실행 비트를 설정할 수 없다 —
  **줄바꿈과 실행 비트는 별개 문제고 둘 다 필요하다.**
- **Dockerfile도 체크아웃 모드를 상속한다:** `COPY gradlew ./`는 644를 그대로 옮기므로 빌드가 죽는다.
  `RUN chmod +x gradlew` 한 줄로 체크아웃 모드에서 독립시킨다.

> 원문: 2026-07-13 「리포 이식성 — 실행 비트가 Windows에서 조용히 유실된다」

# 2. 보안·인가 — 통과하는 테스트가 숨긴 구멍

<a id="2-1"></a>
## 2-1. 새 엔드포인트가 조용히 열린다

- **증상:** 인가 규칙이 `pathMatchers(POST, "/api/index")` 하나였다. 정확 매칭이라 하위 경로는 아무것도
  막지 않아 `/api/index/{key}/reindex`가 "인증만 되면 통과"로 떨어진다.
- **실측:** 일반 사용자 토큰으로 호출하니 403이 아니라 **404**가 돌아왔다 — 보안 필터를 통과해 핸들러
  매핑까지 갔다는 뜻이다. **핸들러가 없어서 404였을 뿐, 컨트롤러가 있었다면 200이다.**
- **처방:** `pathMatchers("/api/index", "/api/index/**").hasRole("ADMIN")` — 메서드와 하위 경로를 가리지
  않는다.
- **핵심:** **인가 테스트는 핸들러가 없어도 의미가 있다.** 403을 기대했는데 404가 오면 그것은 "없는
  엔드포인트"가 아니라 **"인가가 걸리지 않는 경로"** 다. 두 상태를 구분하지 못하면 다음 컨트롤러가 조용히
  문을 연다. **엔드포인트를 만들기 전에** 인가 테스트를 쓴다.

> 원문: 2026-07-10 「SEC — 경로 정확 매칭 인가는 엔드포인트가 늘어나면 조용히 뚫린다」

<a id="2-2"></a>
## 2-2. 남의 세션 ID를 넣으면 그 사람 대화가 샌다

- **증상:** 채팅 스트림이 요청자가 준 `sessionId`를 **검사 없이** 썼다. 소유권 검사 함수는 **이미 있었고**
  세션 조회·삭제는 쓰고 있었다 — 채팅 경로만 건너뛰었다.
- **피해:** 인증된 사용자가 남의 ID를 넘기면 (1) 그 사람의 대화 이력이 프롬프트에 실려 **답변으로 새어
  나오고** (2) 그 세션에 메시지가 덧붙는다. 실측: 대역 모델이 받은 프롬프트에 피해자 문장이 그대로 있었고
  피해자 세션 메시지가 1→3이 됐다.
- **접근 태그 필터는 아무 소용이 없다** — 새는 것이 문서 조각이 아니라 **대화 이력**이다.
- **왜 테스트가 다 통과했나:** **기존 테스트가 전부 자기 세션만 썼다.** 남의 세션을 건드려 본 테스트가
  하나도 없었다. 인가 테스트는 "권한 있는 주체가 성공한다"가 아니라 **"권한 없는 주체가 실패한다"** 를
  봐야 한다. 후자를 쓰지 않으면 통과는 아무것도 증명하지 않는다.
- **처방:** 소유권 확인 후 실패 시 **404**(403이 아니다 — 403은 "그 ID의 세션이 존재한다"를 알려준다).
- **주의:** 세션 ID가 UUIDv4라 추측이 어렵다는 것은 **통제가 아니다.**

> 원문: 2026-07-10 「SEC — 소유권 검사는 "인증됨"과 다르다 (모든 테스트가 자기 세션만 썼다)」

<a id="2-3"></a>
## 2-3. 접근 태그 필터를 거는 위치가 결과를 바꾼다

- **발견:** ES `knn` 절은 자체 `filter` 파라미터를 갖고, 이건 후보군 진입 **전**에 걸리는 pre-filter다.
  반면 Query DSL 트리의 다른 곳에 있는 필터는 kNN에 대해 **post-filter**로 적용된다.
- **왜 문제인가:** post-filter만 쓰면 권한 없는 조각이 후보 풀에 들어왔다가 나중에 제거되고, 결과가 `k`보다
  적어질 수 있다. **"응답에서 제거"와 "검색 단계에서 배제"는 다른 요구다** — 후자를 요구했다면 post-filter는
  문자 그대로 그 요구를 어긴다.
- **처방:** 같은 `terms` 필터를 `knn.filter`와 `bool.filter` **양쪽에** 건다. 이 동작을 실컨테이너 통합
  테스트로 못박는다.

> 원문: 2026-07-10 「SEARCH — `knn` 절의 필터는 pre-filter, `bool` 트리의 필터는 kNN에 post-filter다」

<a id="2-4"></a>
## 2-4. 서명·만료만 보는 JWT 검증은 대상을 좁히지 못한다

- **왜 실재하는 위험인가:** 명시한 클라이언트가 하나뿐이어도 **모든 Keycloak realm에는 기본 클라이언트
  (account·admin-cli·security-admin-console 등)가 암묵적으로 존재**해 같은 realm 키로 서명된 토큰을 발급할
  수 있다. 역할만 맞으면 통과한다.
- **처방:** issuer + audience 검증을 붙인다. **issuer 검증은 정적 문자열 비교라 네트워크 호출이 없다** —
  기동을 막는 설정([6-4](#6-4))과 다른 물건이다. jwk-set-uri(내부 호스트)와 issuer(토큰 `iss` = IdP
  **외부** 호스트명)는 **다른 값**이라 따로 설정한다.
- **audience 함정:** **realm이 내보내 줘야 검증할 수 있다.** 기본 access token은 다른 클라이언트를 `aud`에
  넣지 않는다. 프론트 클라이언트에 audience 매퍼를 걸어야 토큰이 그 값을 담는다.
- **매퍼는 선언적으로:** realm export 파일의 클라이언트 `protocolMappers[]`에 넣으면 개발·운영이 **같은
  파일을 임포트**하므로 매퍼가 **잊힐 수 없다.** 배포별 값(시크릿·redirect)만 스크립트로 얹고, 스크립트
  끝에서 **매퍼 존재를 assert**한다(fail-closed 자가점검 — 임포트 drift를 크게 실패시킨다).
- **함정:** 임포트가 클라이언트를 **먼저** 만들면 부트스트랩 스크립트의 create 분기가 안 탄다 → create에만
  있던 설정이 누락돼 개발 토큰 취득이 깨진다. **update 분기에도 같은 설정을 둔다.**
- **성질:** 두 검증 모두 fail-closed다 — 어긋나면 로그인만 막히고(자기 DoS) 인가 우회는 생기지 않는다.

> 원문: 2026-07-11 「JWT는 서명·만료만으로 부족하다 — issuer·audience로 대상을 좁힌다 (R-16)」 ·
> 2026-07-11 「운영 프론트 Keycloak 클라이언트 프로비저닝 (OQ-012 하위건, 사람 지시)」

<a id="2-5"></a>
## 2-5. 세션에 실은 것은 브라우저가 읽는다

- **증상:** 세션 콜백이 `session.accessToken`을 세웠다. Auth.js는 session 콜백의 반환을 그대로
  `/api/auth/session` 응답으로 내보내므로 **브라우저 JS가 `fetch('/api/auth/session')`로 베어러를 읽을 수
  있었다.** "BFF만 토큰을 쥔다"가 깨진다.
- **처방:** 세션에서 토큰을 빼고 **암호화된 JWT 쿠키에만** 둔다. BFF가 **서버측에서만** 꺼낸다. 재로그인
  판단용 오류 플래그만 세션에 남긴다(민감정보 아님).
- **함정 — 복호화 salt는 쿠키명과 같아야 한다.** 쿠키명이 https에선 `__Secure-` 접두사가 붙는다. 틀리면
  쿠키를 못 찾거나 salt가 어긋나 복호화에 실패해 **모든 BFF 호출이 401**이 된다. 실제 요청 쿠키의 접두사
  유무로 감지해 개발·운영 모두 맞춘다. 큰 토큰이 청크된 쿠키는 라이브러리가 알아서 합친다.

> 원문: 2026-07-11 「세션에 실은 것은 브라우저가 읽는다 — 토큰은 JWT 쿠키에만 둔다 (R-8)」

<a id="2-6"></a>
## 2-6. 에러 메시지를 한 곳만 막으면 다른 통로로 나간다

- **증상:** HTTP 에러 본문에서 예외 문구를 막았는데, SSE `error` 이벤트가 `getMessage()`를 그대로 브라우저로
  보냈다. 실측: 게이트웨이를 멈추고 질문하니 예외 문구(ES 인덱스명·게이트웨이 주소)가 그대로 실렸다.
- **처방:** 고정 문구 + 추적 ID. 원인은 로그에 남고 사용자는 그 ID로 신고한다.
- **핵심:** **에러가 나가는 통로를 세어 본다** — HTTP 본문, SSE 이벤트, 로그, 헤더. 한 곳을 막고
  "막았다"고 적지 않는다.
- **관련:** "부분 응답 후 끊김을 사용자가 구분 가능"은 문구가 아니라 `sources → text… → error`(done 없음)
  **시퀀스**가 만족한다.

> 원문: 2026-07-10 「SEC — 에러 표면은 한 곳만 막으면 소용없다」

<a id="2-7"></a>
## 2-7. 관리 포트를 나눠도 보안 필터체인이 따라온다

- **가정:** `management.server.port`로 액추에이터를 별도 포트에 두면 보안 밖에 놓인다 — **틀렸다.**
- **실측:** WebFlux에서 관리 자식 컨텍스트는 부모의 `WebFilter`(보안 체인)를 그대로 쓴다. 관리 포트 응답에
  `WWW-Authenticate: Bearer`와 우리가 붙인 추적 헤더가 그대로 있었다. **서블릿 스택의 동작을 리액티브에
  그대로 적용하면 틀린다.**
- **처방:** 최우선순위 체인을 하나 더 두고 `securityMatcher`를 **"관리 포트 AND `/actuator/health`"** 로
  좁혀 `permitAll`한다. 경로만으로 열면 앱 포트의 헬스까지 열린다. 관리 포트가 없거나 앱 포트와 같으면
  매치하지 않게 해 **오설정으로 노출되는 경로를 차단**한다.
- **교훈:** 보안 경계에 대한 프레임워크 동작은 **문서가 아니라 응답으로 확인한다.** 이 가정은 테스트를 먼저
  썼기에 잡혔다 — **"관리 포트 200, 앱 포트 401"을 둘 다 단언**한 덕분이다. 한쪽만 단언했으면 통과했다.
- **부수:** 보안 필터체인 빈이 둘이 되면 단일 빈을 주입받던 기존 테스트가 깨진다.

> 원문: 2026-07-10 「OPS — 관리 포트를 분리해도 보안 필터체인은 따라온다 (헬스체크가 401)」

<a id="2-8"></a>
## 2-8. BFF가 상태 코드를 뭉개면 백엔드 인가가 무의미해진다

- **증상:** 스트림 라우트가 **모든 non-2xx를 502로 뭉개고 있었다.** 방금 만든 404·400도, 만료 토큰의 401도
  전부 502가 됐다. JSON 프록시는 상태를 그대로 넘기는데 **스트림 라우트만 달랐다.**
- **왜 치명적인가:** 401을 볼 수 없으면 **토큰 갱신을 붙여도 재로그인을 유도할 수 없다.** 백엔드에서 인가를
  정확하게 만들어놓고 BFF가 그것을 지워버린 셈이다.
- **처방:** 상태·본문을 보존해 릴레이한다. **502는 "상태는 성공인데 본문이 없을 때"만** — 그것이 진짜
  게이트웨이 오류다.
- **교훈:** 백엔드에 새 상태 코드를 추가하면 **그것이 사용자에게 도달하는 경로를 끝까지 따라간다.**
  프록시·게이트웨이·번역 계층이 중간에서 지운다.

> 원문: 2026-07-10 「BFF — 상태 코드를 뭉개면 백엔드의 정확한 인가 응답이 무의미해진다」

<a id="2-9"></a>
## 2-9. 도메인 예외에 상태가 없으면 정상 거부가 500으로 나간다

- **증상:** 업로드 허용목록 위반이 정확히 동작하는데(문서 0행, 조각 0개) 응답이 **500 Internal Server
  Error**다. 클라이언트 잘못을 서버 장애로 보고하는 셈이고, **운영에서 정상 거부와 진짜 장애를 구분할 수
  없다.**
- **처방:** 예외에 상태를 붙인다(`@ResponseStatus(BAD_REQUEST)`). WebFlux가 이를 존중하는지는 **문서가 아니라
  테스트로 확인**했다 — 404·409·400 모두 동작한다.
- **맥락:** 이 프로젝트엔 예외→상태 매핑이 **하나도** 없었다. 처음 하나를 만들 때 함께 정한다.

## 2-10. 업로드 상한은 검증기가 아니라 조인 단계에 있어야 한다

- **증상:** 본문을 메모리로 합치는 호출에 상한 인자가 없어, 거대한 업로드가 **전부 힙에 올라온 뒤에야**
  검증기가 거부했다. 관리자 한 명의 사고성 업로드로 OOM·디스크 소진이 가능하다.
- **처방:** 조인 단계에서 상한을 준다. 초과 시 나는 예외를 도메인 거부(400)로 매핑해 검증기의 거부와 같은
  응답으로 맞춘다.
- **테스트 결정성 함정:** 조인 상한과 검증기 상한이 **같은 값**이면, 상한 초과 업로드는 조인 수정이 없어도
  검증기가 잡아 400을 준다 → **상태코드만 보는 테스트는 수정 유무를 구분하지 못한다.** 서비스가 아예
  호출되지 않았음을 단언해야 결정적이다.

## 2-11. 업로드 MIME은 클라이언트가 말한 값이다

- **처방:** 확장자 + 클라이언트 MIME 허용목록을 **1차 게이트**로 두고, **내용 스니핑(magic bytes)을

  없다.
- **균형점:** 엄격히 "탐지 결과 = 허용목록"으로 하면 탐지기가 못 잡는 포맷·테스트 픽스처를 과도 거부해

  octet-stream으로 잡혀 통과해야 정상이다).
- **검증:** ELF 매직(`0x7F454C46`)을 pdf로 위장해 거부되는지 확인.

## 2-12. 신뢰 못 하는 입력이 가드를 우회해 raw 500이 된다

## 2-14. refresh token은 회전한다 — 새 값을 저장하지 않으면 다음 갱신에서 끊긴다

- **실측:** access token **300초**, refresh token **1800초**. 그리고 **IdP는 처음부터 refresh token을 발급하고
  있었다** — 프론트가 버리고 있었을 뿐이다.
- **회전:** `grant_type=refresh_token`으로 갱신하면 **새 refresh token을 함께 준다.** 회전된 값을 저장하지
  않으면 30분 뒤가 아니라 **다음 갱신에서 바로** 끊긴다.
- **구현:** 갱신 실패를 **던지지 말고** 오류 필드로 표시한다 — 인증 콜백에서 예외가 나면 라이브러리 동작이
  예측하기 어렵다. 실패하면 만료된 베어러를 상류로 보내지 않는다.
- **함정:** **세션 쿠키 수명(기본 30일)과 그 안의 access token 수명(5분)은 완전히 다르다.** 세션이 돌아온다고
  그 안의 토큰이 살아 있는 것이 아니다 — `if (!session)`만 보는 게이트는 갱신 실패를 잡지 못한다.
  **오류 플래그도 봐야 한다.**
- **검증법:** realm의 토큰 수명을 짧게 낮추고 그 시간을 넘겨 동작하는지 본다. 사용자를 비활성화하면 다음
  갱신이 거부되어 재로그인 게이트를 확인할 수 있다.

# 3. 리액티브·비동기 (WebFlux/Reactor)

<a id="3-1"></a>
## 3-1. 블로킹 격리는 `subscribeOn`이지 `publishOn`이 아니다

- **`publishOn`은 하위 연산자만 옮겨 블로킹 소스가 이벤트 루프에 남는다.** 반드시
  `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`.
- **검증은 두 겹으로:** 도구(BlockHound)만 믿지 말고 **실행 스레드 이름이 `boundedElastic-`으로 시작하는지
  단언**하는 테스트를 함께 둔다. 둘이 서로 다른 실패 양상을 잡는다.
- **원칙:** 안전장치는 **위반을 주입해** 검증한다 — "통과했다"가 "위반이 없다"를 뜻하려면 **"위반하면
  실패한다"가 먼저 참**이어야 한다.

> 원문: 2026-07-10 「AUTH/CORE — `issuer-uri`는 기동을 막고, BlockHound는 파일 I/O를 잡는다」

<a id="3-2"></a>
## 3-2. 취소는 `doOnComplete`를 실행하지 않는다 — 감사가 조용히 빈다

- **증상:** 감사 기록이 `doOnComplete`에만 있었다. 근거(sources)는 첫 토큰보다 **먼저** 전달되므로, 사용자가
  근거를 받고 탭을 닫으면(취소) **근거는 이미 브라우저에 갔는데 감사는 0건**이었다. 실측으로 확인 —
  중도 종료 시 감사 카운트가 안 늘었다.
- **처방:** `doFinally`로 옮긴다. **complete·cancel·error 모든 종료에서 정확히 한 번** 돈다. 종료 신호로
  결과(완료/취소/오류)를 구분해 기록한다. **이력은 성공만** 남겨야 하니 `doOnComplete` 그대로 두고 감사만
  분리한다.
- **동시성 주의:** **취소는 진행 중인 `onNext`와 겹칠 수 있다.** `doFinally`가 누적 버퍼를 읽는 순간 다른
  스레드가 쓰는 중일 수 있다(찢긴 읽기 → 드물게 예외). 누적과 스냅샷 읽기를 같은 락으로 묶는다.
  `onComplete`·`onError`는 신호가 직렬화돼 경쟁이 없고 **취소만 예외**다.
- **테스트로 취소 만들기:** `service.stream(...).take(2).blockLast()` — 앞부분만 받고 `take`가 upstream을
  취소한다. 비동기 기록은 래치로 기다린다.

> 원문: 2026-07-11 「감사 공백 — 취소는 doOnComplete를 실행하지 않는다 (R-5)」

<a id="3-3"></a>
## 3-3. `flatMapMany` 매퍼는 upstream onNext에서만 실행된다

- **증상:** [3-2](#3-2)의 종료 훅을 매퍼 **'안쪽'** Flux에 붙였더니, 소스 Mono(검색)가 `onError`일 때 매퍼가
  아예 안 불려 **`doFinally`가 구독조차 되지 않았다** → 검색 실패·조기 취소 시 감사 0건.
- **처방:** 종료 훅을 `onErrorResume` **바깥 최외곽**으로 뺀다. 단 `onErrorResume`이 오류를 삼켜 종료 신호가
  대부분 정상 완료로 오므로, **오류 여부를 별도 플래그로 잡아** 구분한다. 취소는 취소 신호로 구분된다.

<a id="3-4"></a>
## 3-4. 외부 호출 무한 대기는 세 곳이고, 셋째가 제일 어렵다

- **실측:** 응답 없는 소켓(연결만 받고 무응답)에 대해 **200초를 넘겨도** 반환되지 않았다.
- **(a) HTTP 클라이언트:** **JDK HttpClient에는 read 타임아웃 기본값이 없다.** `connectTimeout`은 **연결**
  상한일 뿐 연결 후 무응답은 못 막는다. read를 따로 줘야 둘 다 닫힌다.
- **(b) SSE 스트림:** `Flux.timeout(Duration)`은 전체 응답 상한이 아니라 **토큰 '사이'** 상한이다. 모델이
  조용히 멈추면 에러가 emit되지 않아 `onErrorResume`이 돌지 않는다(done도 error도 안 나감 → **브라우저 무한
  로딩**). `timeout`이 예외를 만들어야 비로소 닫힌다. **토큰이 계속 오는 긴 답변은 잘리지 않는다.**
- **(c) ES 클라이언트:** **기본이 무한이다**(기본 응답 타임아웃 0). 그리고 fluent 트랜스포트 빌더에는 부모까지
  뒤져도 **타임아웃 훅이 없다**(host·auth·ssl·압축·요청옵션뿐). **저수준 클라이언트로 내려가 HTTP 클라이언트를
  직접 물려야** 하고, 그러면 fluent가 해주던 **인증도 직접 보존**해야 한다. "연결은 됐는데 응답이 없다"를
  잡는 것은 **응답 타임아웃**이다.
- **교훈:** **"타임아웃을 넣었다"가 "모든 외부 호출에 넣었다"는 아니다.** 세어 본다.
- **뮤테이션 함정:** 프로덕션에서 타임아웃을 빼면 테스트가 **실패가 아니라 매달린다**(빌드 데몬이 죽었다).
  `block()`·`assertTimeout`에 상한을 주지 않으면 뮤테이션 테스트가 무의미하다.

<a id="3-5"></a>
## 3-5. 추적 ID를 MDC로 옮기는 지점은 블로킹 경계 한 곳이면 된다

- **발견:** 리액티브 전반에 스레드로컬을 전파하는 라이브러리를 붙일 필요가 없었다. 색인·검색·이력·감사 저장이
  **전부 블로킹 격리 래퍼를 지나므로**, 거기서 Reactor Context의 ID를 꺼내 작업 스레드 MDC에 심고 `finally`로
  지우면, 하위 계층이 ID를 인자로 끌고 다니지 않아도 로그가 요청과 이어진다. 새 의존성도, 이벤트 루프에
  스레드로컬을 심는 일도 없다.
- **주의 1 — 인바운드 헤더를 신뢰하지 않는다.** 클라이언트가 보낸 추적 ID를 그대로 쓰면 **감사 기록의
  상관관계 키를 요청자가 고른다.** 항상 서버가 발급하고, **발급처는 하나**여야 한다(컨트롤러가 따로 만들면
  응답 헤더 값과 감사 값이 갈린다).
- **주의 2 — 스레드풀은 스레드를 재사용한다.** 심지 않을 때는 **지운다** — 아니면 앞 요청의 ID를 물려받는다.
- **로그 위생:** 로그에는 질문·답변·조각 **원문을 남기지 않는다**(길이·개수·식별자만). 전문은 감사 로그가 맡는다.

> 원문: 2026-07-10 「OBS — Reactor Context의 추적 ID를 MDC로 옮기는 지점은 블로킹 경계 한 곳이다」

<a id="3-6"></a>
## 3-6. 실패한 요청만 추적이 끊긴다

- **증상:** 관측성을 "마감"했다고 보고한 뒤 500 응답의 추적 ID로 로그를 뒤졌더니 **없었다.** 정상 요청은
  멀쩡하고 **실패한 요청만** 끊긴다 — 하필 추적이 가장 필요한 쪽이다.
- **원인:** 500·404를 찍는 것은 우리 코드가 아니라 프레임워크의 에러 핸들러다. 그 로그 줄은 MDC가 아니라
  exchange의 로그 접두사를 쓴다. MDC는 블로킹 경계 안에서만 심으므로 리액티브 스레드의 에러 핸들러엔 비어 있다.
- **처방 둘:** (1) 필터가 exchange의 **로그 ID 속성을 추적 ID로 덮어쓴다** — 프레임워크가 이 속성을 매번 다시
  읽어 캐시를 무효화하므로(바이트코드로 확인) 모든 프레임워크 로그가 우리 ID를 접두사로 쓴다. (2) 에러 속성을
  확장해 실패 본문에 추적 ID를 싣는다 — 기본 본문의 요청 식별자는 우리 로그 어디에도 없다.
- **교훈:** **"관측성을 붙였다"를 정상 경로로만 확인하지 말 것.** 일부러 500을 내고 응답 헤더의 ID로 로그를
  grep해야 진짜 확인이다.
- **부수:** 예외 메시지를 응답 본문에 포함하는 옵션은 켜지 않는다 — 나가는 것은 추적 ID뿐이고 원인은 그 ID로
  로그에서 찾는다([2-6](#2-6)).

> 원문: 2026-07-10 「OBS — 실패한 요청만 추적이 끊긴다 (에러 핸들러는 MDC를 보지 않는다)」

<a id="3-7"></a>
## 3-7. 검색 결과가 첫 토큰보다 먼저 온다는 보장은 없다

- **상황:** "근거는 서버 검색 결과에서만 나온다"를 프레임워크 RAG Advisor로 구현할 수 있는지 검토했다.
- **발견:** 응답 컨텍스트에서 검색된 문서를 꺼낼 수 있는 것은 사실이다. 그러나 **검색 결과가 첫 텍스트 토큰보다
  먼저 방출된다는 보장은 문서화되어 있지 않다.** 구조상 검색은 모델 호출 전에 끝나지만, 공개 API는 별도의
  "문서 준비됨" 신호를 주지 않고 Flux의 각 요소에 컨텍스트를 붙일 뿐이다.
- **처방:** 채팅이 검색을 **명시적으로 먼저 호출**하고, 받은 조각을 프롬프트에 주입한 뒤 모델을 호출한다.
  근거 이벤트를 첫 토큰 앞에 **확정 발행**할 수 있고, 검색이 진짜 독립 모듈이 된다.
- **교훈:** **프레임워크 내부 방출 순서에 근거의 존재를 걸지 말 것.** 근거의 *원천*이 요구사항이면 그 사실이
  코드 구조에 드러나야 한다.

> 원문: 2026-07-10 「CHAT — 스트리밍에서 검색 결과가 첫 토큰보다 먼저 온다는 보장은 없다」

<a id="3-8"></a>
## 3-8. 클라이언트가 탭을 닫아도 서버는 계속 만든다

- **증상:** BFF의 상류 fetch에 취소 신호가 없고 반환 스트림에 취소 핸들러가 없어, 탭을 닫아도 BFF는 코어를
  끝까지 읽고 코어는 토큰을 끝까지 만든다.
- **처방 두 겹:** (1) 상류 fetch에 요청의 abort 신호를 넘긴다. (2) 반환 스트림의 `cancel()` 핸들러에서 상류
  reader를 취소해 **전파**한다.
- **함정:** `cancel(reason)`에서 상류 reader를 취소하려면 **reader를 `start` 밖(생성자 스코프)에서 만들어**
  둘이 공유해야 한다. `start` 안에서 만들면 `cancel`이 접근할 수 없다.
- **덤:** 채팅 SDK가 이미 `stop()`을 노출하므로, 스트리밍 중 버튼을 "중지"로 바꿔 걸면 **배선돼 있던 취소
  전파와 취소 감사가 그대로 사용자 손에 들어온다.** 새 배관이 필요 없다.
- **실증:** 첫 토큰 수신 후 abort → 감사에 취소로 남았고, 같은 세션의 정상 스트림은 완료로 남았다.

> 원문: 2026-07-11 「BFF 스트림 번역을 라우트와 테스트가 공유 + 취소 전파 (R-14, R-17)」 ·
> 2026-07-12 「스트리밍 잔여 검증 — 직접 BFF fetch + abort→CANCELLED (OQ-012 종료)」

# 4. 데이터·상태 정합성 — 두 저장소 · 색인 · 동시성 · 컨텍스트

<a id="4-1"></a>
## 4-1. 두 저장소 쓰기는 원자적일 수 없다 — 그래서 순서가 방어다

- **증상:** DB upsert(즉시 커밋) → ES 색인 순서였다. ES가 부분 장애(쓰기 차단·매핑 오류·bulk 거부)면 DB 행은
  이미 *현재 모델*로 커밋돼 **유령 문서**가 된다 — **검색 불가인데 stale 판정(모델 불일치)에도 안 잡힌다.**
  실측으로 확인(인덱스 쓰기 차단으로 재현).
- **처방:** **ES 먼저, 성공 후 DB.**
- **핵심 난점:** ES 조각엔 document id가 필요한데 그 id는 지금까지 **커밋이 발급**했다. ES를 먼저 하려면 id가
  커밋보다 **먼저** 필요하다.
- **해법:** **id를 문서 키에서 결정적으로 유도한다**(키가 문서의 정체성이므로 id도 거기서 나오는 게
  자연스럽다). 커밋 전에 조각을 조립할 수 있고, 기존 저장소 시그니처를 안 바꿔 테스트를 대량 수정하지 않아도
  된다.
- **대역 주의:** 결정적 id를 쓰기 시작하면 **모든 저장소 대역도 같은 함수로 id를 발급**해야 조각의 참조와
  저장된 id가 맞는다. 임의 id를 쓰면 통합 테스트 조회가 빈 결과를 준다(이걸로 3건이 깨졌다).
- **남는 위험을 정직하게:** DB 실패-after-ES 성공은 조각만 남지만 접근 태그로 필터돼 안전하고 다음 색인에서
  정리된다. ES **완전** 장애는 차원 검사([4-6](#4-6))가 upsert 전에 ES를 치므로 먼저 실패한다.

> 원문: 2026-07-11 「IDX — 두 저장소 쓰기는 원자적일 수 없다, 그래서 순서가 방어다 (R-3, R-11)」

<a id="4-2"></a>
## 4-2. ES bulk는 원자적이지 않다

- **증상:** bulk 응답에 오류가 있어도 **성공한 op는 이미 반영됐다.** 예외만 던지면 **반쪽 색인이 구버전과
  공존**한다.
- **처방:** 한 번의 bulk가 **한 문서·한 실행의 조각만** 담게 하고, 실패 시 그 문서 id + 실행 id로 **이번 실행의
  조각만 정확히 겨냥해 롤백 삭제**한 뒤 던진다.
- **테스트로 부분 실패 만들기:** 한 조각의 벡터 차원만 다르게 만들어 인덱스 매핑을 위반시킨다(조각 검증이
  "벡터 길이 == 선언된 차원"만 보면 통과하므로 ES까지 도달한다). 롤백을 제거하면 red 되는지 확인한다.

> 원문: 2026-07-11 「IDX — 두 저장소 쓰기는 원자적일 수 없다, 그래서 순서가 방어다 (R-3, R-11)」

<a id="4-3"></a>
## 4-3. 같은 문서를 동시에 색인하면 서로의 조각을 지운다

- **증상:** id가 결정적([4-1](#4-1))이라 같은 키의 동시 색인 두 건이 "구버전 조각 삭제"로 **서로의 조각을
  지워** 조각 0개 + 유령 문서가 된다.
- **처방:** ES색인 → 삭제 → DB커밋 임계구역을 **문서 키 단위 줄무늬 락**(예: 64 stripe)으로 직렬화한다.
  **임베딩은 락 밖**에 둔다(오래 걸린다). 단일 인스턴스 가정이며, 다중 인스턴스면 DB advisory lock이 필요하다.
- **테스트 함정:** **락이 막는 인터리빙은 테스트로 강제할 수 없다** — 겹침을 강제하는 배리어는 데드락이다.
  대신 **겹침을 감지**한다: 임계구역에 지연을 두고 활성 카운터가 1을 넘으면 플래그를 세운다. 락이 있으면
  구조적으로 활성 ≤ 1(결정적 통과), 락을 빼면 겹침과 조각 0개가 잡힌다.

> 원문: 2026-07-11 「코드리뷰 수정 사이클 — F1~F7 (검증 가능한 것부터)」

<a id="4-4"></a>
## 4-4. "찾고 없으면 삽입"은 첫 요청이 동시에 오면 깨진다

- **증상:** 인증 사용자를 로컬 테이블에 넣는 "조회 → 없으면 insert"에서, 같은 신규 사용자의 첫 요청이 동시에
  들어오면 **전부 "없다"고 판단하고 전부 삽입**해 unique 제약을 위반하고 500이 난다.
  **단일 요청 테스트로는 절대 드러나지 않는다.**
- **처방:** 삽입을 `insert … on conflict (<unique 컬럼>) do nothing`으로 **원자화**하고 그 뒤에 읽는다.
  애플리케이션에서 락을 잡는 대신 **DB의 제약을 그대로 쓴다.** 경합에서 진 트랜잭션은 아무것도 하지 않고
  곧이어 이긴 쪽의 행을 읽는다.
- **어떻게 발견했나:** 부하 테스트(동시 요청 32개). **동시성 버그는 부하를 주기 전까지 존재하지 않는 것처럼
  보인다.**
- **관련 번들:** 이 프로비저닝의 전체 설계(어디에 두나 · 무엇을 저장하지 않나)는
  `../keycloak-appuser-provisioning-from-llmhub.md`에 따로 정리돼 있다.

> 원문: 2026-07-10 「CORE — 부하 테스트가 `ensureExists`의 경합 버그를 잡았다」

<a id="4-5"></a>
## 4-5. 한 턴은 한 트랜잭션이어야 한다

- **증상:** 질문 저장과 답변 저장을 **별도 트랜잭션 2번**으로 불러, 답변 저장이 실패하면 **답변 없는 질문만
  이력에 남았다**(fire-and-forget이라 로그만 남는다).
- **처방:** 한 턴(질문 + 답변 + 근거)을 **단일 트랜잭션 메서드**로 묶는다. 세션의 "마지막 활동 시각"도 같은
  곳에서 갱신한다 — 안 그러면 사이드바의 "최근 활동순"이 사실상 **"생성순"** 이 된다.
- **테스트 함정:** **`@Transactional`은 프록시가 있어야 걸린다.** 원자성을 테스트하려고 저장소를 `new`로
  만들면 각 save가 독립 트랜잭션이 되어 **옛 버그 동작이 재현되고 테스트가 거짓 통과·거짓 실패**한다.
  **오토와이어된 빈**을 써야 한다. 시각 갱신은 가변 Clock을 주입해 결정적으로 본다.

> 원문: 2026-07-11 「이력 한 턴은 한 트랜잭션, 활동 시각도 함께 (R-10, R-12) + BlockHound 계측 누적 (테스트 #5)」

<a id="4-6"></a>
## 4-6. 차원 검사는 임베딩 **전에** 한다

- **상황:** 임베딩 차원이 바뀐 채 재색인하면 ES가 거부한다. **임베딩 비용을 쓰기 전에** 막고 싶었다.
- **처방:** 기존 인덱스의 차원을 읽어 설정 차원과 **임베딩 전에** 비교하고, 다르면 409로 거부한다. 실패가
  확정된 작업에 비용을 쓰지 않고 구버전 조각도 건드리지 않는다.
- **테스트:** 예외 타입만이 아니라 **임베딩이 한 번도 호출되지 않았음**을 단언한다.
  **"거부했다"와 "돈을 쓰고 거부했다"는 다르다.**
- **한계:** 차원은 인덱스 생성 시 고정된다. **차원을 바꾸려면 새 인덱스가 필요하고 재색인으로는 안 된다.**
  검색 분석기 변경도 정확히 같은 성질이다.

> 원문: 2026-07-10 「ES/SPRING — 실측으로만 확인되는 두 가지 (매핑 차원, @ResponseStatus)」

<a id="4-7"></a>
## 4-7. 재색인은 재업로드가 아니다 — 진입점 둘, 파이프라인 하나

- **구분:** 재업로드는 **새 파일**을 받고, 재색인은 **보관된 원본**을 다시 읽는다. 그러나 그 뒤 파이프라인
  (추출→청킹→임베딩 전량→bulk 색인→구버전 삭제)은 **완전히 같아야 한다** — 다르면 두 경로 중 하나가 순서
  보장을 잃는다.
- **구현:** 공통 메서드 하나에 **"바이트를 어디서 얻는가"만 다르게** 넘긴다(Supplier). Supplier라서
  **임베딩이 끝난 뒤에 평가**되고, 그 덕에 임베딩 실패 시 고아 원본 파일이 남지 않는다.
- **주의 1:** 재색인은 업로드 검증기를 **부르지 않는다.** 그 바이트는 업로드 때 이미 통과했고, **MIME 타입은
  어디에도 저장되지 않는다** — 검증을 부르면 MIME 정확 매칭에서 반드시 실패한다.
- **주의 2:** 접근 태그는 요청이 아니라 **문서의 현재 값**을 쓴다. **재색인 요청에 태그 인자를 두지 않는 것이
  유일하게 안전한 설계다** — 인자가 있으면 언젠가 그것으로 태그가 바뀐다.
- **주의 3:** 문서 키는 업로드 때 사용자가 정하는 임의 문자열이라 `/`가 들어갈 수 있다 → **경로 변수로는
  주소를 만들 수 없어** 쿼리 파라미터로 받는다.

<a id="4-8"></a>
## 4-8. 파생 쿼리는 실 DB로 검증한다

- **상황:** 재색인 대상 판정을 "임베딩 모델 **또는** 청킹 버전 불일치"로 넓히며 OR 조건 파생 쿼리를 썼다.
- **처방:** 메서드 이름이 맞는지 **이름만 보고 믿지 않고** 실 DB 테스트로 확인한다. 좁은 조건으로 되돌리면
  red가 되는지까지 본다.
- **덤:** 각 문서가 **왜** 대상인지(모델·청킹·둘 다)를 응답에 실어 주면 운영자가 판단할 수 있다.

<a id="4-9"></a>
## 4-9. "최근 N턴"은 길이 상한이 아니다

- **증상:** 요구는 두 줄이었다 — "컨텍스트를 최근 N턴으로 제한"과 "**모델 컨텍스트 길이 초과를 방지하는
  상한**". **앞줄만 구현돼 있었고** 코드에 토큰·문자 상한이 하나도 없었다(grep 0건).
- **원인:** 턴 수는 길이를 잡지 못한다. **긴 메시지 하나면 컨텍스트가 넘친다.**
- **처방 둘:**
  1. 조립기에 **토큰 예산** — N턴으로 자른 뒤 **오래된 쪽부터** 버린다. 예산은 턴이 아니라 **메시지 단위**로
     잘리므로 반쪽 턴이 남을 수 있다. 상한의 목적은 대화 모양이 아니라 초과 방지다. **메시지 하나가 예산보다
     크면 컨텍스트는 빈다** — "최근 것은 무조건 담는다"면 그건 상한이 아니다.
  2. **지금 질문은 자를 수 없다**(잘라내면 사용자가 묻지 않은 것을 묻게 된다) → 길이 초과는 400으로 거부.
- **테스트 태도:** 단언이 실패했을 때 **기댓값을 관측값에 맞추지 않았다.** 산수를 다시 해 예산을 고쳤고,
  "메시지 단위로 잘린다"는 사실은 **별도 테스트로 드러냈다.**

> 원문: 2026-07-10 「PERF — "N턴 제한"은 길이 상한이 아니다」

# 6. 버전·의존성 선택

<a id="6-1"></a>
## 6-1. `latest`가 곧 "우리가 쓸 수 있는 최신"은 아니다

- **증상:** 타입 검사(`tsc --noEmit`)는 통과하는데 `next build`가 `The "id" argument must be of type string.
  Received undefined`라는 **무관해 보이는 메시지**로 죽는다.
- **원인:** `typescript@7`은 **Go 기반 재작성판**이라 `package.json`에 `main` 필드가 없고 `tsc` 바이너리만
  제공한다. Next는 `require('typescript')`로 프로그램 API를 쓴다. **CLI는 되고 API는 안 되는** 상태라
  타입 검사만으로는 절대 드러나지 않는다.
- **처방:** 5.x로 고정. 그리고 커밋 훅에 **빌드**를 추가했다 — 깨끗한 빌드가 6초라 비용이 작고, **타입 검사가
  못 잡는 부류**를 잡는다(훅이 실제로 빌드 실패를 차단하는지 일부러 깨뜨려 확인했다).
- **교훈:** **메이저 재작성판이 `latest`를 차지할 수 있다.** 그리고 **"타입 검사 통과"는 "빌드 성공"이
  아니다** — 검증 수단을 하나만 두면 그 수단이 못 보는 층이 통째로 비어 있게 된다.

> 원문: 2026-07-10 「CLIENT — `typescript@7`은 JS API가 없다. 타입 검사는 통과하고 빌드가 죽는다」

## 6-2. Spring AI 메이저는 Boot 메이저를 끌고 온다

- Spring AI 2.0은 **Boot 4.x + Framework 7**을 요구한다(Jackson 3, Jakarta EE 11 베이스라인 변경 동반).
  Boot 3.x에 남으려면 1.1.x 라인이다. 버전 실재는 레지스트리에서 직접 확인했다.
- **부수 발견 셋:**
  - 두 종류의 RAG Advisor는 **각자 독립적으로 검색을 수행하는 대안 관계**다. 한 체인에 둘을 넣으면 검색이
    두 번 돌고 컨텍스트가 두 번 주입된다.
  - Spring AI의 ES VectorStore는 **kNN 전용**이며 BM25와의 하이브리드를 지원하지 않는다 — `VectorStore`

  - 그래서 하이브리드가 필요하면 VectorStore를 쓰지 않고 **ES 클라이언트로 직접 쿼리**한다. 조각 메타와
    접근 태그를 정확히 통제할 수 있어 색인 쪽에도 유리하다.
- **주의:** 오래된 튜토리얼은 옛 패키지 경로를 쓰므로 import가 틀린다. `spring-ai-core`는 없어졌다.

## 6-4. `issuer-uri`는 기동 때 IdP로 네트워크 호출을 낸다

- **처방:** `jwk-set-uri`는 첫 검증 때 지연 조회하므로 컨텍스트가 뜬다. **issuer 검증이 필요하면 정적 문자열

## 6-6. 채팅 UI SDK는 메이저에서 요청 조립 방식이 바뀐다

- **(a) `useChat`은 SSE의 `event:` 이름을 읽지 않는다.** `data:` 안 JSON의 `type` 필드로 파트를 구분하고,

- **(c) SSE 청크 경계는 프레임 중간을 자른다.** 버퍼에 남긴 마지막 조각을 다음 청크와 이어붙이지 않으면

## 6-7. 하이브리드 랭킹 기법은 라이선스 티어를 확인하고 고른다

- **상황:** BM25 + 벡터 결합에 RRF를 쓰려 했다.
- **발견:** 벤더의 구독 표는 무료 티어로 표시하지만, **같은 벤더의 기술 블로그는 상위 라이선스가 필요하다고
  적고 있고** 커뮤니티엔 무료 티어에서 라이선스 비준수 오류가 난 사례가 있다. **유료→무료 전환 버전은
  확인되지 않았다.** 설치형이면 고객의 ES 버전을 우리가 통제하지 못한다.
- **처방:** 최상위 `knn` 절 + `query` 절을 **한 요청**에 넣어 ES가 두 점수를 **합산**하게 하고 절별 `boost`로
  가중한다. 무료 티어에서 확실히 동작하고 "단일 쿼리" 요구도 지킨다. 병합기는 그 위의 **얇은 어댑터**로 두어
  나중에 교체 가능하게 한다.
- **주의:** BM25 점수와 벡터 점수는 **스케일이 달라** boost 튜닝이 필요하다.

## 6-8. 리액티브 스택은 설정만으로 보장되지 않는다

- 서블릿 스타터가 섞이면 **두 갈래**로 갈린다: (1) `spring.main.web-application-type=reactive`가 **없으면**
  컨텍스트 자체가 서블릿이 된다. (2) 설정이 **있어도** 컨텍스트는 리액티브로 유지되지만 웹서버가 Netty가 아니라
  **Tomcat(reactive)** 으로 바뀐다. **설정만으로는 방어되지 않는다.**
- **처방:** **컨텍스트 타입과 서버 타입을 각각** 단언하는 테스트를 둔다. 두 단언이 서로 다른 실패 양상을 잡는다.
  다른 스타터가 **전이 의존**으로 서블릿 스타터를 끌어올 수 있으니 의존성 추가 후 반드시 돌린다.

> 원문: 2026-07-10 「INFRA — `web-application-type: reactive`만으로는 Netty가 보장되지 않는다」

## 7-1. 통과하는 스위트가 방어의 부재를 숨긴다 → 뮤테이션

## 7-3. 대역이 재현하지 못하는 것을 "테스트했다"고 적지 않는다

- **증상:** 컨트롤러 테스트로 MIME 불일치를 재현하려 했더니 **200이 나왔다.** 프레임워크의 메시지 라이터가
  **파일명에서 Content-Type을 다시 유도**해 테스트 클라이언트로는 MIME을 속일 수 없다. 실제 클라이언트
  (`curl -F 'f=@x;type=...'`)는 속일 수 있다.
- **함께 — 0바이트 업로드는 클라이언트마다 다르다.** curl은 멀티파트 파트를 **아예 빼버리고**(프레임워크 400,
  검증기 미실행), 테스트 클라이언트는 **길이 0 버퍼를 보낸다**(우리 검증기 400). 에러 메시지를 켜고서야 구분됐다.
- **처방:** 그 경로는 **단위 테스트가 막는다**고 적고, 통합 테스트가 그걸 검증한다고 적지 않는다.
- **그리고 로그의 부재로 코드 경로를 추론하지 말 것** — 그 로그가 검사 뒤에 있는지 앞에 있는지 먼저 본다.
  이 함정으로 앞선 기록이 실제로 한 번 틀렸다(나중에 정정).

## 7-4. 컨테이너 대기 조건은 테스트가 실제로 의존하는 상태여야 한다

- **증상:** 인증 테스트가 간헐 실패했다(재실행하면 통과).
- **원인:** 대기 전략이 **"200 또는 401 응답"** 이었다. 보안이 켜진 ES는 **HTTP 계층이 먼저 401을 돌려주기
  시작하고, 사용자를 담는 네이티브 렘은 그 뒤에 초기화**된다. 그 틈에 인증하면 실패한다.
  **401을 "떴다"의 신호로 쓴 것이 원인이다.**
- **처방:** **"자격증명이 실제로 통한다"**(basic auth + 200)를 기다린다.
- **왜 중요한가:** 간헐 실패는 커밋 훅(전체 테스트 실행)을 무작위로 막고, **"red를 무시해도 된다"는 습관**을
  만든다.

## 7-5. 통합 테스트 컨테이너는 모으고, JVM은 주기적으로 재활용한다

- **컨테이너는 JVM당 하나로 모은다**(정적 싱글턴). 클래스마다 띄우면 통합 테스트가 몇 배 느려지고, 훅이 매
  커밋마다 전체 스위트를 돌리면 그 비용이 곧바로 개발 속도에 꽂힌다.
- **BlockHound는 JVM 전역·영구 계측이다.** 테스트 클래스와 여러 컨텍스트가 한 JVM에 누적되니 어느 순간 계측
  에이전트의 **네이티브 할당이 실패**했다. 테스트 단언 실패가 아니라 **JVM 크래시**라 빌드 도구가 "실행을
  완료할 수 없음"으로 보고한다 — **헷갈리기 쉽다.**
- **처방:** `forkEvery`(예: 15) + 힙 상향. JVM을 주기적으로 재활용해 누적을 끊는다. fork는 순차 실행이라
  컨테이너 피크 자원은 그대로다.

## 7-7. 아키텍처 규칙의 와일드카드가 서드파티를 잡는다

- **증상:** ES 클라이언트를 도입하자 "이 모듈은 다른 모듈에 의존하지 않는다" 규칙이 **갑자기 실패**했다.
- **원인:** ArchUnit의 `..search..`는 "이름에 `search` 세그먼트가 들어간 **모든** 패키지"를 매치한다.
  라이브러리 내부 패키지(`co.elastic.clients.elasticsearch.core.search`)가 걸린 **오탐**이다.
  `..chat..`·`..idx..` 등도 같은 위험이 있다.
- **처방:** 규칙을 **완전한 패키지 접두사**(`com.<우리>.search..`)로 좁힌다. **규칙을 약화시킨 것이 아니라
  의도한 규칙으로 바로잡은 것**이다.
- **함께:** ArchUnit 1.x는 규칙이 검사할 클래스를 하나도 못 찾으면 **실패**한다(패키지명 오타 방지 목적).

  들어오면 규칙이 실제로 동작하기 시작한다.
- **주의:** 빌드 도구의 테스트 필터(`--tests`)가 아키텍처 테스트를 걸러내지 못해 항상 함께 실행될 수 있다.

## 7-8. 바이너리 픽스처는 코드로 만든다

- 저장소에 바이너리를 커밋하거나 생성 라이브러리를 의존성에 추가하지 않아도 된다. PDF는 규격대로

- **이점:** 내용이 코드로 드러나 리뷰 가능하고 의존성이 늘지 않는다. PDF 본문은 **ASCII만** 담는다 —
  한국어를 넣으려면 폰트 임베딩이 필요한데, 이 테스트가 확인하려는 것은 **추출 경로이지 폰트가 아니다.**
- **한계를 정직하게:** 픽스처를 라이브러리로 만들고 **같은 라이브러리로 읽으면** 검증되는 것은 **어댑터
  배선**이지, 실제 워드프로세서가 저장한 파일과의 호환성이 아니다. 후자는 진짜 샘플이 필요하다.

## 7-9. 부하 측정은 워밍업을 분리한다

## 7-10. 테스트가 못 켜는 모듈은 순수 부분을 분리한다

- 프레임워크·인증 모듈을 import하는 파일은 경량 테스트 러너(예: `node --test`)로 **켤 수 없다.** 스트림

  **무검출**이었다.
- 부수: Node의 실험적 타입 스트리핑은 **생성자 파라미터 프로퍼티**를 지원하지 않는다(타입만 지우고 코드를

## 7-11. 주석은 검증이 아니다 (세 번 나왔다)

이 프로젝트에서 **똑같은 형태로 세 번** 나왔다:

1. "전부 설정값이며 코드에 하드코딩하지 않는다"고 적힌 클래스가 **분석기를 하드코딩**하고 있었다.
2. "전략이 바뀌면 이 값으로 재색인 대상을 식별한다"고 적힌 상수가 **전략과 무관**했다.
3. "컨텍스트 길이 초과를 방지한다"고 적힌 조립기가 **턴 수만 제한하고 길이는 제한하지 않았다.**

**공통점: 주석이 코드보다 앞서 있었다.** 주석이 주장하는 성질은 **테스트로 옮긴다.**

## 7-13. 색 토큰 위에 CSS를 세우면 다크모드가 거의 공짜다

- 모든 규칙이 `var(--token)`이면 다크 테마에서 **색 토큰 몇 개만 리매핑**해도 전부 따라온다. 배경/전경이
  **함께 뒤집히는 토큰 쌍**을 쓰면 대비가 자동으로 유지된다. `color-scheme`도 같이 넘겨 스크롤바·입력창 같은
  네이티브 컨트롤이 테마를 따르게 한다.
- **FOUC + 하이드레이션 함정:** 페인트 전에 테마를 확정하려면 `<head>`의 **동기 인라인 스크립트**가 필요한데,
  그러면 서버 HTML엔 없던 속성을 클라이언트가 붙여 **하이드레이션 불일치 경고**가 뜬다 → 해당 요소에 한해
  경고를 억제한다(정석 패턴). **토글 글리프는 테마 무관 고정**으로 두고 라벨(방향)만 마운트 후 확정해야 안전하다.

# 8. 컨테이너·기동·레포 위생

> 이 묶음은 `../infra-for-onggijonggi/compose-checklist.md`와 **의도적으로 겹친다.** 그 번들에는 compose
> 관점의 처방이, 여기엔 지도 전체의 맥락이 있다.

<a id="8-1"></a>
## 8-1. 앱은 멀쩡한데 컨테이너가 unhealthy

- **증상:** 헬스체크 로그는 `can't connect to remote host: Connection refused`인데 라우트는 200이다.
  `127.0.0.1`로는 되고 `localhost`로는 거부된다.
- **원인:** Alpine 등에서 `localhost`가 **`::1`(IPv6)로 먼저 풀리는데** 서버는 `0.0.0.0`, 즉 **IPv4에만
  바인딩**한다.
- **처방:** 헬스체크 URL을 **`127.0.0.1`로 고정**한다.
- **함께:** `docker ps` 상태를 `grep -c healthy`로 세면 **`unhealthy`가 매치된다** — 이 오탐 때문에 처음엔
  통과한 줄 알았다. **상태 문자열은 정확히 비교한다.** 그리고 **헬스체크가 실제로 통과하는 것을 눈으로
  본다** — `condition: service_healthy`는 헬스체크가 틀리면 조용히 기동을 막거나 영영 unhealthy로 남는다.

> 원문: 2026-07-10 「OPS — 컨테이너 헬스체크의 `localhost`는 ::1로 풀린다 (서버는 IPv4에만 바인딩)」

<a id="8-2"></a>
## 8-2. 이미지에 curl·wget이 없다

- 최신 Keycloak 이미지는 minimal이라 curl/wget이 없다. 하지만 **`/bin/sh`가 bash라 `/dev/tcp`가 된다.**
  헬스 엔드포인트를 켜면 **관리 포트 9000**에 준비 상태 경로가 뜬다(개발 모드에서도 동작 — health는 모드
  무관). 실측: 재생성 후 ~25초에 healthy.
- `node:alpine`에도 curl이 없다(wget은 있다).
- **헬스체크는 컨테이너 생성 시 박히므로** 적용하려면 `up -d --force-recreate <svc>`가 필요하다.
  (그리고 IdP 컨테이너를 재생성하면 내장 DB가 리셋되니 부트스트랩을 다시 돌린다 — [8-12](#8-12).)

> 원문: 2026-07-12 「자잘한 하드닝 마감 — 업로드 MIME 스니핑(L-11)·KC healthcheck(L-9)」

<a id="8-3"></a>
## 8-3. ES는 "HTTP 200"과 "사용자 준비 완료"가 다르다

→ **[7-4](#7-4)** 참조.

<a id="8-4"></a>
## 8-4. postgres가 healthy인데 접속이 거부된다

- **증상:** 최초 기동에서 백엔드가 `Connection refused`로 즉사한다.
- **원인:** postgres가 **init 스크립트를 도는 도중** 소켓으로 준비 검사(`pg_isready`)를 통과시켜 compose는
  "healthy"로 보는데 **TCP는 아직 안 열려 있다.**
- **처방:** init이 끝난 뒤 **`up -d`를 한 번 더** 돌리면 붙는다. 근본적으로는 **restart 정책**이 있으면 자동
  복구된다(이 사고는 restart 정책이 없어서 커진 것이다).

> 원문: 2026-07-12 「브라우저 E2E 검증 — Playwright + 격리 운영 스택 (B1·F3·OQ-012)」

<a id="8-5"></a>
## 8-5. 로컬 PostgreSQL이 5432를 가로챈다 (오진하기 쉬움)

- **증상:** 마이그레이션이 `password authentication failed for user "..."`로 죽는다.
- **원인:** 로컬에 설치된 PostgreSQL이 `0.0.0.0:5432`를 잡고 Docker는 `[::]:5432`(IPv6)만 잡는다 → 호스트에서
  `localhost:5432`로 나가는 연결이 **컨테이너가 아니라 로컬 서버로 간다.** 그쪽엔 그 비밀번호의 사용자가 없다.
- **오진 함정:** `docker compose exec postgres psql -U <user>`는 **잘 된다.** 컨테이너 내부는 trust 인증이라
  **틀린 비밀번호로도 통과한다.** "DB는 멀쩡한데 앱만 못 붙는다"로 보여 비밀번호·줄바꿈·빌드 데몬 환경변수를
  먼저 의심하게 된다.
- **처방:** 개발 포트를 **5433**으로. compose 매핑과 앱 datasource URL이 같은 변수를 쓰면 한 곳만 고치면 된다.
- **진단:** 리스너가 둘인지 본다(`netstat -ano | grep :5432`). **컨테이너 내부 접속으로 비밀번호를 검증하지
  않는다.**

> 원문: 2026-07-10 「INFRA — 로컬 PostgreSQL이 5432를 가로챈다 (compose 포트 충돌, 오진하기 쉬움)」

<a id="8-6"></a>
## 8-6. 로그 회전이 없으면 며칠 뒤 스택이 통째로 멈춘다

- Docker 기본 json-file 로그는 **크기 제한이 없다** → 호스트 디스크 소진 → DB WAL 실패·ES read-only 전환.
- **처방:** YAML 앵커로 한 번 정의해 **모든 서비스**에 건다(예: max-size 10m / max-file 5).
- **검증:** `docker compose --env-file <파일> -f docker-compose.yml config`가 앵커·env를 해석해 최종 서비스
  정의를 뱉는다. compose는 유닛 테스트가 없으니 **이 resolve가 검증**이다.

> 원문: 2026-07-11 「배포 설정 위생 — 설정이 코드에 닿지 않으면 없는 것이다 (R-6, R-7, R-15)」

<a id="8-7"></a>
## 8-7. `mem_limit`이 없으면 JVM이 호스트 전체를 기준으로 힙을 잡는다

- cgroup 제한이 없으면 JVM(`MaxRAMPercentage`)이 **호스트 전체 RAM**의 비율로 힙 상한을 잡아, 단일 호스트의
  다중 JVM이 물리 메모리를 초과해 **OOM-kill**된다. 각 서비스에 상한을 두면 JVM이 **그 몫 기준**으로 잡는다.
- 상한 합계는 호스트 사양에서 역산한다(모델 런타임이 호스트에 함께 뜬다면 그 몫도 남긴다).

> 원문: llmhub `.env.example` 「서비스 메모리 상한」 주석 (리뷰 지적 사항) —
> 이 항목만 `LEARNINGS.md`가 아니라 설정 파일 주석이 출처다.

<a id="8-8"></a>
## 8-8. 운영 compose가 base, 개발이 override

- **문제였던 상태:** compose 하나로 개발·운영을 겸하니 ES 보안 꺼짐, IdP dev 모드, 모든 포트 개방이 그대로
  **고객에게 나가는 산출물**이었다.
- **처방:** `docker-compose.yml`을 **운영 기준**으로 두고 `docker-compose.override.yml`이 개발용 완화를 얹는다.
  앱 컨테이너는 프로파일로 묶어 개발에선 소스로 돌린다.
- **운영에서는 `-f docker-compose.yml`을 명시해야 한다** — override가 저장소에 있으면 `docker compose up`이
  **조용히 얹어 보안을 완화한다.**
- **설계 버그였던 것:** **IdP를 내부망에만 두면 로그인이 불가능하다.** 브라우저가 OIDC 리다이렉트로 직접
  접근해야 한다. "내부망 전용" 목록에 IdP가 없었는데 **목록을 정확히 읽지 않았다.**
- **IdP 운영 모드는 실제 DB를 요구한다**(내장 임베디드 DB는 dev 전용). 같은 PostgreSQL 인스턴스에 별도
  데이터베이스를 만들어 붙였다 — init 스크립트는 **데이터 디렉토리가 비어 있을 때만** 실행된다.
- **검증법:** 별도 프로젝트명·별도 데이터 루트·다른 포트로 운영 스택을 **실제로 띄운다**([8-15](#8-15)).
  `docker compose port`는 **어느 파일 조합으로 해석했느냐에 따라 다른 답**을 준다 — 실제 바인딩은 `docker ps`로
  본다.

> 원문: 2026-07-10 「INFRA — 운영 compose는 base, 개발은 override (REL-5)」

<a id="8-9"></a>
## 8-9. `.gitignore`의 선행 슬래시는 루트만 잡는다

- **증상:** e2e 테스트가 업로드한 원본 27개가 **여러 커밋 전부터 추적되고 있었다.**
- **원인:** `/data/`는 **선행 슬래시 때문에 저장소 루트만** 잡는데, 테스트는 작업 디렉토리가 하위(`backend/`)라
  `backend/data/...` 아래에 쓴다.
- **처방:** `data/`로 쓰면 어느 깊이에서든 잡는다. **`.gitignore` 패턴은 작업 디렉토리가 바뀌는 경우를
  상상해서 쓴다.** 그리고 **`git add -A <디렉토리>`는 무시되지 않는 산출물을 조용히 삼킨다.**
- **원칙:** 문서 저장 루트가 저장소 안에 있으면 **언젠가 새어 나간다.**

> 원문: 2026-07-10 「SEC — `.gitignore`의 선행 슬래시가 업로드 원본을 놓쳤다」

<a id="8-10"></a>
## 8-10. 셸 문자열에 백틱을 넣지 않는다 — 문서의 명령이 실행된다

- **증상:** `node -e "..."` 안에서 README의 코드 펜스를 치환하려다, bash가 백틱을 **명령 치환**으로 해석해
  **README 코드 블록의 내용을 그대로 실행했다** — `docker compose up -d`까지 돌아 컨테이너 넷이 떴다.
- **처방:** 문서 파일 수정은 셸을 거치지 않고 편집 도구로 한다. 여러 줄 문자열이 필요하면 heredoc(`<<'EOF'`)을
  쓰되 **그 안에도 백틱을 넣지 않는다.**
- **원칙:** 셸 명령을 조립할 때 **"이 문자열이 셸에 해석될 여지가 있는가"를 먼저 묻는다.**
  백틱·`$(...)`·`$VAR`는 인용 안에서도 살아난다. 부작용 있는 명령이 문서에 적혀 있다면 더더욱.

> 원문: 2026-07-10 「TOOLING — 셸에 마크다운 코드 펜스를 넣지 말 것 (의도치 않은 명령 실행)」

## 8-11. Git Bash(Windows)는 인자를 경로로 바꾼다

<a id="8-12"></a>
## 8-12. IdP 개발 계정: 프로필이 비면 로그인이 막힌다

- **증상:** 계정을 만들고 토큰을 받으려는데 `invalid_grant: Account is not fully set up`.
- **원인:** 최신 Keycloak의 **선언적 사용자 프로필**은 email·이름·성을 필수로 본다. 비어 있으면 프로필 확인
  필수 액션이 걸린다. **그런데 사용자의 `requiredActions`는 빈 배열로 보여** 역할·비밀번호·활성화 여부를 아무리
  확인해도 원인이 안 나온다. **세 필드를 채우면 즉시 해결된다.**
- **처방:** 부트스트랩 스크립트가 프로필 세 필드를 항상 채운다. 비밀번호·시크릿은 환경 파일에서 읽고
  **재실행 가능**하게 만든다.
- **realm import는 최초 기동 때 한 번만 적용된다.** 컨테이너 재생성(볼륨 초기화) 시 배포별 값이 사라지므로
  해당 환경 부트스트랩을 다시 돌린다.
- **덤:** 실제 IdP 토큰으로 백엔드를 처음 때려봤을 때 비로소 **서명 검증과 역할 파싱이 진짜로 도는지**가
  검증됐다. 그전까지 모든 테스트가 디코더를 대역으로 썼기 때문이다.

> 원문: 2026-07-10 「INFRA — Keycloak 개발용 계정: 프로필이 비면 로그인이 막힌다」 ·

<a id="8-13"></a>
## 8-13. 게이트웨이의 "No connected db"는 키가 틀렸다는 뜻이다

- **증상:** 색인 중 500. 원인은 게이트웨이가 준
  `{"error":{"message":"No connected db.","type":"no_db_connection"}}`.
- **원인:** LiteLLM은 마스터 키와 **다른** 키를 받으면 **가상 키로 간주해 DB를 조회**하고, DB가 없으니 이렇게
  답한다. **키 불일치라는 진짜 원인을 전혀 드러내지 않는다.** (여기서는 앱 기본값 `changeme`와 환경 파일의
  `change-me`가 달랐다.)
- **처방:** 키를 맞추면 **다음 오류로 넘어간다**(`model ... not found, try pulling it first`) — 두 오류는 서로
  다른 층이다. **`No connected db`를 보면 DB가 아니라 키를 의심한다.**
- **함께:** 빌드 도구 데몬은 **나중에 export한 환경변수를 물려받지 않는다** — 데몬을 끄거나 인자로 직접 넘긴다.

> 원문: 2026-07-10 「INFRA — LiteLLM의 "No connected db"는 키가 틀렸다는 뜻이다」

<a id="8-14"></a>
## 8-14. 커밋 훅이 도는 동안 워킹트리를 건드리지 않는다

- 훅이 **워킹트리를 읽어** 빌드·테스트를 돌리므로, 백그라운드 커밋이 도는 중에 다음 커밋용 파일을 수정하면
  **빌드가 그 중간 상태를 읽는다.**
- **처방:** 커밋은 백그라운드로 돌리되 **완료를 확인하고** 다음 파일 작업을 시작한다.
- **팀에서는 더 크게 온다** — 같은 워킹트리를 여러 도구·여러 사람이 동시에 읽는 상황을 만들지 않는다.
  (그리고 훅이 전체 스위트를 돌면 컨테이너 기동 flake로 가끔 실패한다 — 재시도로 통과.)

<a id="8-15"></a>
## 8-15. 격리 스택으로 운영 구성을 검증한다

- **방법:** 별도 프로젝트명 + 별도 환경 파일 + 별도 데이터 루트 + 시프트한 포트로 운영 compose를 띄우면
  **개발 스택을 파괴하지 않고** 운영 구성을 검증할 수 있다.
  예: `docker compose -p <이름> --env-file <파일> -f docker-compose.yml up -d --build`
- **`--env-file`의 중복 키는 마지막이 이긴다** — 기본 파일을 복사하고 끝에 오버라이드를 덧붙이면 된다.
- **`docker compose exec`는 어느 `-f`로 시작했든 같은 컨테이너에 붙는다** — 그래서 운영용 부트스트랩
  스크립트를 현재 컨테이너에 그대로 실행해 전 로직을 검증할 수 있다(검증 후 개발 설정 복원 필요).
- **데이터 볼륨 경로를 변수로 두면**(`DATA_ROOT`) 운영 구성을 개발 데이터를 파괴하지 않고 검증할 수 있다.

## 8-16. 빈 스택에서 채팅은 실패한다 (인덱스가 없다)

- 문서를 하나도 색인하지 않으면 조각 인덱스가 없어 검색이 `index_not_found`로 실패한다 → 채팅이 오류 이벤트로
  끝난다.
- 성공 스트림을 브라우저로 보려면 **먼저 관리자로 문서 1건을 색인해야 한다.** 팀이 처음 스택을 띄우고
  **"채팅이 안 된다"고 오인하기 쉬운 지점**이다.
